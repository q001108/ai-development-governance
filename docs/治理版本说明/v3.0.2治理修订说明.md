# v3.0.2 治理修订说明

版本：v3.0.2；状态：`COMMUNITY-BASELINE`；社区发布日期：2026-10-19。

## 适用边界

本社区版在 v3.0.1 的通用接入基线上同步“已确认的新业务基线替代旧基线”能力。三档 Profile、人工业务验收、候选隔离、失败归因、验证调整及人工 Git 交付边界继续适用，不引入完整自动运行时。

接入项目必须在自身 `AGENTS.md` 中明确启用日期与适用范围，并为新需求绑定 v3.0.2。历史及执行中需求不自动迁移、不重编号、不改写事件；执行中需求只有在逐项记录迁移批准并满足本说明全部绑定条件后，才能使用新版替代路径。发布本社区版不表示任何项目已完成采用或迁移。

## 新 G1 重基线

业务目标、期望结果或用户明确约束在 G1 后变化时，仍须修订需求基线并取得新的人工 G1。若旧开发上下文包已经冻结，新 G1 导致旧业务能力退出范围，ControlProfile v3.0.2 必须增加非空 `BaselineSupersession`；初版与普通计划修订使用 `null`，继续执行既有单调保护。

`BaselineSupersession` 必须同时满足：

- `Mode=G1_BASELINE_SUPERSESSION`；
- `PreviousG1Ref` 与前版全部用户需求来源的 G1 完全一致；
- `CurrentG1Ref` 与新版全部用户需求来源的 G1 完全一致，且事件时间晚于旧 G1；
- 新需求基线版本严格递增；
- `SupersededAcceptanceSourceIds` 精确覆盖前版中被删除或改变的用户需求来源，不得包含未变化来源或正式业务契约；
- `SupersededControls` 精确覆盖前版中被删除或改变的已触发阻断 BA/RB/QG；每项必须同时引用当前需求基线与当前 G1；
- `HistoricalArtifactRefs` 与 `HistoricalArtifactDigests` 在当前 Requirement 的 `history/` 下保留重基线前 ControlProfile 和 AcceptancePlan 原文及摘要；即使前版未提交，也不得只保留文字概述；
- `HistoricalSourceDisposition` 默认使用 `FULLY_REPLAYABLE`。只有旧检查点客观上未提交其引用的基线/G1 时，才可使用 `DIGEST_ONLY_LEGACY_SOURCE_UNAVAILABLE`，并通过 `HistoricalSourceEvidenceRefs` 同时绑定历史 Profile 快照、原 G1 和带版本历史的当前基线；正式业务契约不得使用此兼容状态；
- `HistoricalArtifactsRetained=true`、`PriorCandidatesReusable=false`、`NewG2Required=true`。

满足上述条件只允许新版计划不再继承明确列出的旧控制，不表示自动通过风险判断。新版 Profile、AcceptancePlan 与开发上下文包仍须完整校验，重新规划并取得人工 G2。旧 Profile、Plan、G1/G2、候选、Writer、QA、Reviewer、路由及人工决定全部只读保留，不得删除、覆盖、改绑或作为新候选证据复用。

被替代控制是否确实只服务于已经退出的业务能力，由规划者提供可审查依据并在新 G2 中由人工确认。仍适用的安全、权限、迁移及共享契约风险不得借业务重基线省略；未解决的硬触发、用户或正式契约下限继续约束新版判级。

## 版本与机器校验

ControlProfile、AcceptancePlan 的 `SchemaVersion`、`GovernanceVersion` 和 ControlProfile 的 `DecisionRulesVersion` 使用 v3.0.2。`BaselineBindings.Governance` 绑定本说明；测试基线未变化，`BaselineBindings.Testing` 继续绑定 [v3.0.1 测试规范](../开发规范/测试规范.md)，各自独立核验来源、摘要与可选 Git revision。

事件 envelope 仍使用 v1.1，机器 `FactProtocolVersion` 仍使用 v2.1，不把文档版本直接写进机器协议字段。v3.0、v3.0.1 契约继续按各自版本校验，不补新字段；旧需求沿用原绑定文档内容或固定 revision，不能把本次发布当作其历史结论变更。

`validate-plan` 对存在前版的计划执行两条互斥路径：

1. `BaselineSupersession=null`：保持原有单调规则，禁止降档、移除硬触发、修改原业务来源以及删除或改变旧阻断控制。
2. `BaselineSupersession` 非空：只对声明且精确覆盖的新 G1 替代项开放变化；漏报、多报、旧 G1 冒用、非递增基线、缺少新基线/G1 依据或允许复用旧候选均失败。

校验 Git 前驱时，若前版 BAS 的 `ProvenanceRevision=null`，v3.0.2 只在已验证的重基线路径中使用 `PreviousProfileRevision` 读取旧需求基线和旧 G1。若前驱确实没有提交来源文件，摘要兼容状态只保留旧 Profile 中已经存在的 `SourceDigest`，不声称重新核验了缺失原文；旧 G1 摘要、事件结构、版本和当前基线历史仍须通过。普通当前文件不得借此前驱或兼容状态规避摘要校验。

该兼容路径不是通用的未提交计划版本链，也不授权中间 commit。校验器不推断自然语言语义或自动生成批准，机器通过仅证明其已检查的字段、来源、版本、时间、集合覆盖及历史保留不变量。

沿用只读校验命令：

```powershell
python scripts/governance_tools.py validate-plan --control-profile <path> --acceptance-plan <path>
python scripts/governance_tools.py validate-g2 --control-profile <path> --acceptance-plan <path>
```

`validate-g2` 返回资格信息，不创建 G2 决定；重基线路径仍需人工确认新 G2。任何校验成功均不等于 QA PASS、Reviewer APPROVE 或人工业务验收。

## 社区兼容适配

本次移植保留社区已有的 Windows、macOS、Linux 本地支持、可配置交付平台、通用开发规范入口及社区 Schema 标识；不导入任何特定业务项目的模块、品牌、部署条件、真实需求或迁移批准。

v3.0.2 继续使用 [v3.0.1 修订说明](./v3.0.1治理修订说明.md)中既有的失败归因、同轮恢复、受控验证调整与质量汇合规则。本说明将这些增量章节原来“仅 v3.0.1”的适用范围扩展至明确绑定 v3.0.2 的需求，原文及历史绑定不改写；开发者编号和 `BaselineBindings` 同样继承，只有治理绑定改为 v3.0.2。

社区工具与总控、QA、Reviewer 角色入口同步识别 v3.0.2；调整记录的 `GovernanceVersion` 必须与其绑定 Profile 精确一致，不能混用 v3.0.1 与 v3.0.2 的调整事实。原有候选、证据、独立评审、人工批准和覆盖条件不放宽，旧版结果不回填新字段。

社区校验还将重基线资格的 `RequiredG2DecisionMode` 固定为 `HUMAN`，并把保留的历史 Profile、Plan 快照与所绑定 Git 前版的规范化原文摘要核对。只修改历史快照并重算其自报摘要仍会失败；摘要兼容状态仅允许缺失旧业务来源原文，不允许伪造旧 Profile 或 Plan。这些检查落实本说明已有的人工 G2 与历史原文保留要求，不替代人工语义判断。

发布检查同时覆盖 v3.0.1 与 v3.0.2 修订说明。测试仅使用临时仓库和合成场景，不包含或复现真实需求数据。

## 采用与交付

本版本不自动 commit、push、merge、发布或部署，不默认假设 CI、内网服务、审批平台或生产验证存在。项目必须声明真实环境与职责；本地结果不能外推为其他平台或生产通过。

完整事件持久化、候选生成、自动派发、路由执行、跨机器协调及通用模板升级不属于此次同步。主智能体或项目工具仍须按既有事实协议承担运行时责任，历史与执行中需求继续保持自身版本边界。
