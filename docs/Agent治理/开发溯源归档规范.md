# 开发溯源归档规范

规范状态：`FROZEN`
版本：v3.0
生效日期：2026-09-16

## 目的与边界

本文档只定义 `开发记录.md` 的生命周期，以及开发溯源归档智能体在人工业务总验收后的核验、工程交付登记和最终冻结职责。机器事实、运行时投影与恢复遵循[治理运行时事实协议](./治理运行时事实协议.md)，字段呈现遵循[开发记录模板](./开发记录模板.md)。

开发溯源归档智能体不参与需求分析、实现、临时质量验证、只读评审、路由或 UCR，也不负责开发期间的 Markdown 投影。

## 开发记录生命周期

`开发记录.md` 在 G2 冻结后由运行时初始化，是单需求目录的人类可读入口。

| 记录生命周期状态 | 进入条件 | 维护责任 |
|---|---|---|
| `IN_PROGRESS` | G2 已冻结，运行时已初始化计划任务点 | 运行时 |
| `IMPLEMENTED` | 当前有效任务点均有完成、经批准取消或替代事实 | 运行时 |
| `VERIFIED` | LEAN 的触发 RB/QG 已全部通过；或 STANDARD / CONTROLLED 已完成 AcceptancePlan 要求的独立质量角色和适用汇合；已有进入 BA 的事实 | 运行时 |
| `ACCEPTED_PENDING_MERGE` | 人工业务总验收通过，阶段 1 核验完成 | 开发溯源归档智能体 |
| `FROZEN` | 目标工程交付完成、必要交付事实补齐且全局需求版本登记成功 | 开发溯源归档智能体 |

状态只能从已有事实投影，不得人工跳级或用下游结果反推缺失事实。阻塞、取消或重新规划时保留现有事实，不得伪装为完成状态。

运行时在候选处置、进入人工验收、人工验收完成和最终归档等稳定边界刷新开发记录。时间线只保留生命周期、候选处置、质量汇合、人工验收和工程交付状态跃迁，不逐条复制 QA / Reviewer 事件。Markdown 可从不可变事实重建，但不得反向补造事实；投影 `PENDING` / `STALE` 不阻塞开发路径，最终归档前必须追平。

## 人工验收后的两阶段归档

| 阶段 | 触发条件 | 核验与写入 | 完成状态 |
|---|---|---|---|
| 1：验收核验 | 已有事实明确表明人工业务总验收通过 | 先依据原始事件追平同一份开发记录，再核验质量汇合与人工验收引用。必要交付事实尚未形成时标记“待补充”，不适用字段不构成缺失 | `ACCEPTED_PENDING_MERGE` |
| 2：最终溯源与版本登记 | 项目实际采用的目标工程交付流程已经完成 | 补齐必要交付事实和实际适用的条件事实；形成原始需求摘要与最终实现功能摘要；登记 `docs/需求版本管理.md` 唯一记录并核对一致性 | `FROZEN` |

归档只有以上两个阶段。阶段 1 不得宣布最终冻结；阶段 2 缺少必要交付事实或全局登记时不得冻结，也不得增加第三阶段。

最小启动输入：阶段 1 需要人工验收事实、同一需求的开发记录及其原始事件；阶段 2 还需要阶段 1 完成事实、目标工程交付事实和全局唯一键核验结果。

工程溯源按以下边界记录：

- 必须交付事实：目标工程流程或目标分支、最终交付提交人、提交时间、已经存在的 `BusinessDeliveryCommitSHA`；
- 条件适用事实：开发分支、MR、CI、审批、合并时间、Merge Commit SHA；
- 实际发生才记录：版本、发布和部署。

通用规范不要求所有项目必须使用 代码托管平台、MR、CI 或线上部署；项目级 `AGENTS.md` 已选择交付路径时以该选择为准，不适用或未发生的条件事实不得虚构。

业务交付与归档事实必须分为两个提交：人工验收后创建的 `BusinessDeliveryCommit` 包含摘要绑定产物但不能引用自身 SHA；其后 `ArchiveFactCommit` 才能记录已存在的 `BusinessDeliveryCommitSHA`。`ArchiveFactCommitSHA` 由 Git 元数据或再后续事实观察，不能写入该提交自身树。不得为写回任一 SHA 修改需求基线、G1 事实或已经绑定的 `SourceDigest` / `ApprovalDigest`；`ProvenanceRevision` 只是可选来源快照，不承担最终提交自引用。

存在已合并 MR 时，交付责任人和交付完成时间分别取 MR 作者与实际合并时间；无 MR 且直接交付目标分支时，分别取业务交付 Commit 的提交者与 Commit 时间。

## 事实绑定与记录规则

- 所有输入必须绑定同一 `RequirementId`。任务事实保持 `WorkPackageId`、`WriterRound` 绑定；候选相关验证和评审事实还保持 `ContextPackVersion`、`RepairLineageRef`、`CandidateRef` 和角色轮次绑定。
- 归档只消费已经持久化、可定位且完成敏感信息检查的事实。仅有 Markdown 摘要而缺少原始事实时，不得完成最终冻结。
- 阶段 Markdown 或开发记录显示 `PENDING` / `STALE` 时，应从已校验事件追平投影，不得要求重跑 QA、Reviewer 或路由；投影追平失败时才阻止最终冻结。
- BA/RB/QG/AD 投影与冻结计划对照按[开发记录模板](./开发记录模板.md)填写。LEAN 保留五份最小固定 Git 产物但不创建空 QA/Reviewer 投影；STANDARD / CONTROLLED 保留完整记录职责。工具生成区块仅减少排版，不承担本规范的归档核验。
- 原始需求摘要和最终实现功能摘要各保持一至三句，分别来自已批准需求和最终交付事实。QA、评审和人工验收结论必须原样引用；未执行事项不得写成完成或通过。
- 不得收录完整智能体对话、内部推理、完整路由正文、完整 Git 差异、大段源码、完整日志、人员工时或 Token 统计。允许保存 Profile 规定的分钟预算、验证项 `EstimatedMinutes` 与角色事件脱敏 `DurationMs` 聚合；不得将其冒充人员绩效或完整墙钟。不得传播脱敏前的日志、截图、JSON 或疑似敏感值。
- 全局需求版本唯一键为 `RequirementId + 需求迭代版本`。相同唯一键且内容一致视为幂等完成；内容冲突时必须停止，不得覆盖或重复追加。

## 权限

开发溯源归档智能体只允许：

- 阶段 1 更新运行时指定需求的同一份 `开发记录.md`；
- 阶段 2 继续更新该记录，并向 `docs/需求版本管理.md` 追加或依据稳定工程事实纠正当前唯一记录。

它不得修改其他需求记录、业务源码、候选、需求基线、开发上下文包、治理文档或模板；不得改变范围、契约、任务状态、验证 / 评审 / 人工验收结论；不得批准 UCR，也不得操作 代码托管平台、提交、合并、推送、发布或部署。
