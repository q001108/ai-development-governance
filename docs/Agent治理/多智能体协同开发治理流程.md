# 多智能体协同开发治理流程

状态：`FROZEN`
版本：v3.0
生效日期：2026-09-16

## 目的

本文档定义 多智能体协同开发的治理生命周期、候选验证回环和终止边界。
现有 `多智能体协同开发治理流程-v1.5.svg` 仅对应历史 v1.5 流程，不表示 v3.0。

v3.0 的 `GovernanceProfile` 判级、`BA / RB / QG / AD` 控制分类、LEAN 精简路径及机器校验唯一遵循[治理配置与验收控制规范](./治理配置与验收控制规范.md)。本文未被 Profile 改写的候选、计数和恢复规则继续适用；第一阶段不实现完整状态机或自动路由改造。

若图示与本文存在歧义，以本文为准。

## 标准流程

以下只展示两道门禁均通过的成功路径。G1 `REJECTED` 或尚未决定时不得进入技术规划；G2 `REJECTED` 或尚未决定时不得冻结上下文包、初始化开发记录或启动写入。

原始需求 → 运行时形成需求基线
↓
G1：人工需求确认形成 `CONFIRMED` 决定
↓
运行时保存 G1 `GATE_DECISION`，以稳定路径、版本和内容摘要绑定基线与批准事实
↓
运行时技术只读审计，形成 DRAFT `ControlProfile` / `AcceptancePlan` / 开发上下文包，并按 `CONTROLLED → STANDARD → LEAN` 求出规划下限
↓
LEAN 由主智能体承担精简规划；STANDARD / CONTROLLED 调用总控编排器执行规划；三份 DRAFT 协同补齐工作包、BA/RB/QG/AD 与预算
↓
运行时重新判级并执行 `validate-plan`；三者一致后由 `validate-g2` 核验 live 资格
↓
G2：形成 `FROZEN` 决定
↓
运行时保存 G2 `GATE_DECISION`；决定为 `FROZEN` 时冻结上下文包
↓
运行时按 Profile 初始化需求级 Git 记录；`开发记录.md` 始终保留
↓
执行模式选择
↓
写入执行者按 `WorkPackageId` 实现并输出修改事实
↓
运行时保存写入交接，并更新任务点、代码修改事实和过程时间线
↓
候选状态
↓
运行时保存不可变候选事实
↓
LEAN 由 Writer 执行触发的 RB/QG；STANDARD / CONTROLLED 按 AcceptancePlan 启动独立质量角色
↓
保存实际发生的验证与评审事实；不得为空角色制造记录
↓
STANDARD / CONTROLLED 沿用版本化质量汇合；LEAN 第一阶段由运行时依据已校验计划人工编排，不新增自动路由协议
↓
STANDARD / CONTROLLED 保存适用路由事实；LEAN 保存现有 Writer 交接及逐项证据引用，第一阶段不生成自动路由；Markdown 在稳定阶段边界异步投影
↓
人工业务总验收
↓
开发溯源归档：核验并补齐同一份开发记录
↓
人工提交并推送 代码托管平台 → 人工批准与合并
↓
开发溯源归档：补齐工程事实、登记 `docs/需求版本管理.md` 并冻结记录
↓
完成

STANDARD / CONTROLLED 中实际触发的 QA 与 Reviewer 结果先分别保存为不可变事实，再由运行时按本文件的版本化规则处理。LEAN 不要求两个角色或双结果汇合；其触发 RB/QG 全部通过后才可进入 BA。正常 PASS、APPROVE、可唯一映射的失败、结构化前置阻塞和终止阈值不得重复调用总控重判；只有绑定冲突、无法唯一映射、疑似治理边界变化、需要重规划或事实矛盾时才调用 `EXCEPTION_ROUTING`。Markdown 投影不在质量关键路径，不得因投影延迟阻止另一角色、自动路由或恢复。敏感信息保护优先于原样持久化。

## G1、G2 与 UCR 边界

G1 只确认需求基线是否准确表达用户的业务目标、期望结果和明确约束。G1 不是 UCR，不进行技术范围、影响面、风险、契约、工作包、验证或执行模式审计；这些内容在 G1 确认后由运行时只读审计求出初始 Profile 下限，再由 LEAN 主智能体精简规划或 STANDARD / CONTROLLED `EXECUTION_PLANNING` 与三份 DRAFT 契约协同收敛。G1 必须有明确、可定位的人工确认，不得由智能体代批或把沉默视为确认。运行时将决定持久化为绑定当前需求基线版本的 G1 `GATE_DECISION`，并以稳定路径、实际产物版本、`SourceDigest` 与 `ApprovalDigest` 形成可恢复绑定；中间阶段不要求 Git commit。尚未形成明确决定时，需求基线保持待确认状态且不产生门禁事件。

G2 是开发上下文包的执行就绪决策。v3.0 只有 `ControlProfile` 与 `AcceptancePlan` 已通过机器校验才可形成 G2。`DecisionMode` 表示决定如何形成，开发上下文包的 `DRAFT` / `FROZEN` 表示产物状态，两者不得混用：

- `AUTOMATIC`：只允许校验结果为 `RequiredG2DecisionMode=AUTOMATIC_ALLOWED` 的 LEAN 或 STANDARD。两者都必须满足：需求基线/G1及两份计划契约绑定明确；范围、归属、契约、BA/RB/QG/AD、风险、任务点、依赖、角色、平台、预算和执行模式完整一致；不存在 CONTROLLED 硬触发、未知项、冲突、实施阻塞或用户取舍；验证命令无业务源码修改副作用。LEAN 还必须满足全部 LEAN 资格；STANDARD 可以命中 STANDARD 升级条件，但不得命中 CONTROLLED 硬触发。`AUTOMATIC` 不得产生 `REJECTED`。
- `HUMAN`：CONTROLLED 必须使用 HUMAN；LEAN / STANDARD 若存在触发的 `DETERMINISTIC_ASSERTION`，也必须使用 HUMAN，由人工确认每项断言只映射一个风险目标；存在必须由用户作出的产品、业务或方案取舍时同样使用 HUMAN。人工决定形成并被上下文包吸收前保持 `DRAFT`；完成必要规划后，人工可以形成 `FROZEN` 或 `REJECTED`。自然语言断言的语义原子性无法可靠自动判定，无法确认时升级 STANDARD。
- `N/A`：任何必要事实未知、缺失、冲突、不可定位，或范围、契约、风险、验证、任务点、依赖及证据边界尚未闭合时，表示尚未形成决定，开发上下文包必须保持 `DRAFT`。未知风险不得以 `AUTOMATIC` 或笼统人工决定绕过。

G2 决策类型和依据必须投影到开发上下文包的 G2 冻结节：`AUTOMATIC` 记录白名单逐项满足的事实；`HUMAN` 记录人工门禁及决定依据；尚未形成决定时记录 `DecisionMode=N/A` 和阻塞项。必要信息未知、缺失、冲突或规划未闭合时不产生 G2 `GATE_DECISION`。已形成的 G2 决定使用 `FROZEN` 或 `REJECTED`；运行时必须先保存绑定当前开发上下文包版本的 G2 `GATE_DECISION`，并在决定为 `FROZEN` 时冻结该上下文包，之后才可初始化开发记录。决策模式不能替代开发上下文包自身的 `DRAFT` / `FROZEN` 状态；`REJECTED` 后上下文包保持 `DRAFT`。

UCR 只处理开发上下文包 `FROZEN` 后的治理变化。冻结前的技术规划调整由总控编排器继续在 `DRAFT` 上下文包中完成，不进入 UCR。G1 确认后，如果业务目标、期望结果或已确认约束发生变化，必须修订需求基线并重新执行 G1；不得用 UCR 或 G2 批准替代新的需求确认。冻结后的范围、契约、归属边界或受保护面变化进入 UCR；其他冻结计划变化按既有重新规划路径处理。

历史及执行中需求仍按其绑定的治理版本和模板版本解释，不自动迁移或改写。

## 核心规则

1. 原始需求不能替代冻结上下文包作为完整写入依据。
2. G1/G2/UCR 按上一节执行，不从后续成功反推前置门禁。
3. 上下文包完整记录范围、归属、契约（如需要）、验收、风险、验证及执行模式；任务点统一为 `WorkPackageId`，具有摘要、计划操作、边界、依赖及完成条件，字段见[上下文包模板](./开发上下文包模板.md)。
4. 已确认业务目标或约束变化重新 G1；冻结后治理变化按上一节进入 UCR 或重新规划。
5. 每条候选的临时质量验证、只读评审与路由事实必须绑定其自身的运行时 `CandidateRef`，以及同一 `RequirementId`、`ContextPackVersion`、`RepairLineageRef`；临时质量验证和只读评审分别还绑定 `QARound`、`ReviewerRound`，路由单独绑定 `RoutingRound`。`CandidateRef` 必须引用不可变候选事实，不得只引用可变工作区路径。普通候选修复后的后续轮次使用新的 `CandidateRef`，仍归属同一关联链；任何既有验证结果或证据均不得跨 `CandidateRef` 复用或改绑。字段缺失、冲突或跨 `Requirement`、开发上下文包、关联链时不得推测、合并记录或合并计数。
6. 写入交接、候选、测试就绪、临时质量验证、只读评审与路由 JSON 是原始事实源。运行时在稳定阶段边界为需求级 Markdown 和开发记录最小摘要排队异步投影；投影不得进入角色或路由关键路径，时间线只记录关键状态跃迁，不逐条复制角色事件。临时质量验证和 Reviewer 均不得写入、覆盖或修订阶段记录。
7. 运行时在同一 `Requirement`、当前 `FROZEN` 开发上下文包与关联链内，从不可变事件历史投影两类连续质量失败计数：`CountDisposition=ACTIVE` 时，临时质量验证只有 `FAIL` 增加 QA 失败计数，`BLOCKED` 保持计数不变；只读评审者的 `CHANGE` 增加 Reviewer 失败计数。已经存在终结候选处置时才到达的任何迟到结果只保存原始结论，使用 `CountDisposition=IGNORED_DUE_TO_PRIOR_DISPOSITION`，不增加、归零或以其他方式改变连续计数。普通候选修复不重置计数。计数不得作为脱离事件历史的可编辑事实。
8. `CountDisposition=ACTIVE` 的临时质量验证 `PASS` 仅重置 QA 失败计数，只读评审者 `APPROVE` 仅重置 Reviewer 失败计数，且均不删除既有轮次。冻结后经 UCR 或重新规划产生新的 `FROZEN` 开发上下文包时，两类计数从零重新开始，但旧开发上下文包 / 关联链的轮次和原因必须保留。
9. 任一角色当前连续质量失败计数达到 3 时，运行时按版本化规则形成 `Status="BLOCKED"`、`Decision=null`，自动回派停止。阻塞汇总必须仅依据该角色三轮失败事实，列出每轮原因及候选、轮次、证据引用；不得把环境等待计入或重新判断原因。
10. 终止后，只有可定位的明确人工恢复，或经 UCR / 重新规划形成新的 `FROZEN` 开发上下文包，运行时才可重新启动。人工恢复必须明确适用角色、关联链与新的连续计数起点；信息不足时维持 `BLOCKED`。
11. STANDARD / CONTROLLED 的 QA 派发前逐项执行 `TEST_READINESS`；就绪子集先运行、前置等待不占轮次、阻塞不计质量失败、完整有效集合与同候选复验按[协议“测试就绪与增量复验”](./治理运行时事实协议.md#测试就绪与增量复验)执行。LEAN 不创建空 QA/Reviewer 轮次，按已校验 AcceptancePlan 完成触发的 RB/QG 后进入 BA。
12. 所有需求均保留 Git 版本化记录。LEAN 最小固定记录为需求基线、`control-profile.json`、`acceptance-plan.json`、轻量开发上下文包和开发记录；STANDARD / CONTROLLED 保留五份中文配套记录并增加两个 JSON。开发记录是单需求入口，不再新建需求索引。各产物区分治理版本、模板版本、产物版本和当前状态，顶部保留稳定引用。目录、ID、历史英文别名及双文件冲突统一按[事实协议](./治理运行时事实协议.md#文件名与历史兼容)解释，历史文件不自动迁移、删除或改名。
13. 新需求统一存放于 `docs/requirements/<RequirementId>/`；事件、幂等与恢复按事实协议。
14. 开发记录在 G2 后初始化、稳定边界异步刷新；人工验收后核验、工程交付后登记全局台账并最终冻结，按[归档规范](./开发溯源归档规范.md)。全局台账不成为需求事实源。

## 候选质量汇合与路由

v3.0.1 增量规则：环境等待解除沿用原逻辑 QA 轮次，详细绑定见事实协议；冻结验证方法需要纠正时采用[治理修订说明](../治理版本说明/v3.0.1治理修订说明.md)中的独立调整记录。运行时派发及汇合前均重新核验 AdjustmentRef/AdjustmentDigest、候选及有效控制覆盖，只有新的完整 QA PASS 与同候选 Reviewer APPROVE 汇合才进入人工验收。调整校验通过不是质量通过；无解除证据的环境阻塞不重复派发、不重新规划、不消耗质量失败额度。本补充不新增 ROUTE 枚举，也不重算历史计数。

本节路由表在 v3.0 第一阶段只适用于 STANDARD / CONTROLLED 中实际同时触发 QA 与 Reviewer 的路径。候选事实保存后，两者原则上并行。运行时只按下表的客观条件生成路由；单独收到 QA `PASS` 或 Reviewer `APPROVE` 时，`JoinState=PENDING`，不生成路由事件，也不进入人工验收。LEAN 的自动路由属于后续阶段，本版不得伪造 `ROUTE-*` 结果。

| RuleId | 客观条件 | 自动结果 |
|---|---|---|
| `ROUTE-000` | 本轮没有任何已触发且归属 QA 的项目可执行，且至少一个 `BLOCKING` 项的逐项就绪状态为未就绪；阻塞类型、责任方和恢复条件完整 | `WAIT_FOR_PREREQUISITE`；不创建 QA 轮次，解除前不得重派 |
| `ROUTE-005` | QA 连续 `FAIL` 或 Reviewer 连续 `CHANGE` 达到 3 次 | `Status=BLOCKED`、`Decision=null`，停止自动回派；优先级高于其他正常规则 |
| `ROUTE-006` | 在当前候选尚无终结处置时，QA `FAIL` 与 Reviewer `CHANGE` 均已保存，均未达终止阈值，全部失败 / 发现可唯一映射现有工作包，且无治理边界变化 | 一次 `RETURN_TO_WRITER`，受影响工作包取两类事实的并集 |
| `ROUTE-001` | 同一候选的 QA `PASS` 与 Reviewer `APPROVE` 均已保存，绑定和摘要一致，QA 有效阻断验证集合完整 | `READY_FOR_HUMAN_ACCEPTANCE` |
| `ROUTE-002` | QA `FAIL`，未达终止阈值，当前尚无 Reviewer `CHANGE`，失败可唯一映射现有 `WorkPackageId` / 写入槽位，且无治理边界变化 | `RETURN_TO_WRITER`，返回映射的失败工作包；修复形成新候选后重新执行完整有效验证集合 |
| `ROUTE-003` | Reviewer `CHANGE`，未达终止阈值，当前尚无 QA `FAIL`，发现可唯一映射现有工作包，且无治理边界变化 | `RETURN_TO_WRITER` |
| `ROUTE-004` | 已创建 QA 轮次且 QA `BLOCKED`，阻塞类型、责任方和恢复条件完整，且无候选失败或治理边界变化 | `WAIT_FOR_PREREQUISITE`；解除前不得立即重派 QA |

以下情况不允许套用正常规则，必须调用总控编排器 `Invocation: EXCEPTION_ROUTING`：绑定或候选摘要冲突；失败 / 发现无法唯一映射工作包；疑似改变冻结范围、契约、归属边界或受保护面；需要改变冻结验收、风险、验证集合或执行模式；QA 与 Reviewer 对同一事实存在不可机械调和的矛盾；没有命中任何版本化规则。总控只做异常分类，不重判正常 PASS / APPROVE。

规则匹配按 `ROUTE-005`、`ROUTE-006`、其他规则的优先级判断，并以每次判断时已经持久化的事件快照为准。每个候选只能有一个终结其当前处置的路由。QA `FAIL`、Reviewer `CHANGE` 或终止阈值先形成终结路由后，应尽力取消另一并行角色；无法取消的迟到结果仍可保存，但必须引用已有 `DispositionRef`，标记 `CountDisposition=IGNORED_DUE_TO_PRIOR_DISPOSITION`，不得增加计数、再次路由旧候选或改变既有处置。QA `BLOCKED` 和 `ROUTE-000` / `ROUTE-004` 只进入可恢复等待，不终结候选；同一候选的 Reviewer `APPROVE` 可以保留并在阻塞解除后的 QA 汇合中继续使用。

## 执行模式

由当前 Profile 的规划责任方根据任务依赖选择：

- `SINGLE`
- `DEPENDENCY-SEQUENTIAL`
- `BOUNDED-PARALLEL`

不得为了使用多智能体而强行并行。

## 治理规范自身变更控制

治理规范和模板使用 `DRAFT → REVIEWED → FROZEN → SUPERSEDED` 生命周期。`FROZEN` 文档不得原位修改后继续使用同一版本号。

治理规范升级必须记录变更原因、影响范围、兼容性、旧版本、新版本、评审依据、批准依据、生效时间和对执行中需求的处理方式。历史需求继续绑定其已记录的治理版本；升级不得自动改写历史需求产物。正在执行的需求是否迁移必须逐项决定，回滚也必须形成新的可定位治理事实，不得删除版本历史。
