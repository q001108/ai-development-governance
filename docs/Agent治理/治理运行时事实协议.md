# 治理运行时事实协议

状态：`FROZEN`
版本：v3.0
生效日期：2026-09-16

## 目的

本文档定义需求治理过程中机器事实的目录结构、事件类型、稳定标识、任务执行事实、候选绑定、计数投影、持久化顺序、幂等恢复、需求迭代版本和敏感信息处理边界。

本文档不定义需求审批、业务验收、实现方案或角色职责；这些内容仍由[多智能体协同开发治理流程](./多智能体协同开发治理流程.md)、[Codex 运行时拓扑](./Codex运行时拓扑.md)和当前开发上下文包定义。

## 需求目录与标识

所有新需求的治理产物必须存放于：

`docs/requirements/<RequirementId>/`

`RequirementId` 必须使用 `REQ-YYYYMMDD-NNN`：

- `REQ` 固定大写；
- `YYYYMMDD` 使用 `Asia/Shanghai` 时区对应的自然日期；
- `NNN` 为同一日期内从 `001` 开始的三位十进制序号；
- `RequirementId` 创建后不得修改、复用或分配给其他需求；
- 取消、拒绝或终止的需求仍保留原 `RequirementId`；
- 同一需求的修复、UCR 或重新规划不得创建新的 `RequirementId`；
- 目录名必须与治理 JSON 中的 `RequirementId` 完全一致。

Markdown 展示名称 `Requirement ID` 与 JSON 字段 `RequirementId` 表示同一标识符。主智能体 / 运行时负责根据现有目录分配并复核唯一 ID；总控编排器只原样使用该 ID。重复或冲突时必须停止，不得覆盖、合并或静默改号。

## 需求目录结构

### v3.0.1 增量规则：开发者标识与新需求编号

明确绑定 v3.0.1 的新需求使用 `REQ-<DeveloperId>-<YYYYMMDD>-<Sequence>`，例如 `REQ-DEV-20260917-01`。旧 `REQ-YYYYMMDD-NNN` 保持原名、原引用和原版本，工具兼容读取；本节不迁移历史需求。

DeveloperId 由开发者首次初始化时显式提供，优先 代码托管平台 用户名，也可使用团队登记的唯一短代号。统一转大写，1～32 位 ASCII 字母、数字、点、下划线或连字符，首尾须为字母或数字，不允许连续两点；不合格式的用户名使用登记短代号。不读取或修改 Git user.name，不把提交署名当成身份唯一性证明。标识大小写不构成不同身份。

初始化与分配命令（从仓库根目录执行）：

```powershell
python scripts/governance_tools.py init-developer --repo . --developer-id DEV
python scripts/governance_tools.py reserve-id --repo .
```

初始化只写本地仓库 `governance.developerId` 配置，不入业务提交；关联 worktree 共享配置。重复相同标识是幂等操作，已设置不同标识时停止，不静默更改。确需更换时由开发者显式修改该本地配置，只影响之后的分配，历史 ID 不变。独立 clone 需要分别初始化。缺失或多值配置会提示初始化/纠正，不从本机用户名、邮件或远端 URL 猜测身份。

`reserve-id` 以 Asia/Shanghai 自然日期和至少两位当日序号分配；超过 99 后自然增长。扫描可访问关联 worktree、当前本地已知分支/远端跟踪引用/标签，以及 Git common directory 内的预留目录，然后以原子目录创建领取号码。它只写共享的本机 Git 元数据，不创建需求基线、不修改产品文件、不自动 fetch/commit/push。运行时收到返回 ID 后仍需核对目标需求目录，再创建实际需求；不得把重新调用 reserve-id 当成既有任务的恢复方式。

并发分配保证限于同一 Git common directory。中断可能消耗号码，预留不自动回收，序号不要求连续。预留目录不进入版本控制，不能随重要缓存一起清理后继续假定所有未提交编号可发现。独立 clone、未同步远端和不同机器的同账号不受该原子预留保护：创建前同步已知需求，同账号跨机器由人员协调分配或使用登记的唯一短代号。发生已分配 ID 冲突时停止处理，禁止覆盖、合并或静默改号；不得宣称本机工具提供全局唯一性。

需求标题独立维护，目录只用 ID；负责人、标题或账号后续变化均不重命名既有需求。配置共享语义依据 [Git worktree 配置文档](https://git-scm.com/docs/git-worktree#_configuration_file)，元数据路径依据 [Git rev-parse 文档](https://git-scm.com/docs/git-rev-parse)；本次在 Git 2.54.0.windows.1 验证。

v3.0 的所有需求至少形成需求基线、`control-profile.json`、`acceptance-plan.json`、开发上下文包与开发记录五份固定 Git 版本化产物，其中 `开发记录.md` 是单需求入口；`RecordRefs` 在 G2 前声明全生命周期计划路径，但后置文件不得因此提前创建。LEAN 的上下文包只投影单工作包和必要控制，不复制两份 JSON。QA / Reviewer 投影只在 STANDARD / CONTROLLED 实际触发对应角色时创建。`facts/` 下的 JSON 是运行事实源，两个计划 JSON 是冻结前的控制契约；Markdown 不得反向覆盖任一机器契约或事实。v2.1.1 历史目录仍按其绑定版本解释，不要求补文件。

## v3.0 计划契约

`control-profile.json` 和 `acceptance-plan.json` 的规范 Schema 分别为 [ControlProfile Schema](./contracts/control-profile.schema.json) 与 [AcceptancePlan Schema](./contracts/acceptance-plan.schema.json)，语义唯一遵循[治理配置与验收控制规范](./治理配置与验收控制规范.md)。运行时必须在 G2 冻结和 Writer 启动前执行：

```powershell
python scripts/governance_tools.py validate-plan --control-profile <path> --acceptance-plan <path>
```

默认 live 模式只接受本 Requirement 目录内的固定文件并返回 `Mode=LIVE / G2Eligible=true`。`--mode replay` 仅供历史反事实分析并返回 `Mode=REPLAY / G2Eligible=false`。G2 只调用独立 `validate-g2` 入口，不能把 `validate-plan` 的退出码当作 G2 资格。

校验器必须先对 ControlProfile 与 AcceptancePlan 执行 Schema 实例校验，再重新计算 Profile，而不是信任调用方填写的 `SelectedProfile`；必须核验全部触发器与 LEAN 资格闭集、最低等级、业务来源闭集、BA 原文等价、控制类别不变量、角色、预算和跨文件绑定。Schema 无法表达的跨文件、摘要、聚合、归一化等价、语义指纹及回放一致性由 Python 语义层继续校验。校验失败不得冻结、实施、生成候选或通过删除字段降级。

两个文件采用版本链而非原位抹除已经生效的决定：首次固定为 `ProfileVersion/PlanVersion=v1.0`，四个前版引用与 revision 字段均为 null；已固化的后续版本用前版引用和实际 revision 绑定前版。G1 后未完成需求的 BAS 以稳定路径、产物版本、`SourceDigest`、`ApprovalDigest` 及可选来源快照 `ProvenanceRevision` 绑定事实；摘要不一致立即失败。最终人工验收后才由人工创建 `BusinessDeliveryCommit`；该提交不能引用自身 SHA。后续独立 `ArchiveFactCommit` 只记录已经存在的 `BusinessDeliveryCommitSHA`，其自身 SHA 只能从 Git 元数据或再后续事实观察，不能写入自身树。任何阶段都不得为写入 SHA 而改写需求基线或已绑定摘要，任何中间阶段不得自动 commit。基线实际版本、G1 版本与 BAS 版本必须三方相等。

计划返回的 `RequiredG2DecisionMode` 为结构化责任边界：存在任一触发的 `DETERMINISTIC_ASSERTION` 时固定为 `HUMAN`，人工须确认每项只映射一个风险目标；否则为 `AUTOMATIC_ALLOWED`，仍不等于已经形成 G2 事实。自然语言断言的语义原子性不在机器保证范围，无法确认时升级 STANDARD。

1. 优先使用运行时或治理记录提供的稳定显式路径；

4. 同类型中英文文件同时存在且没有稳定引用时停止处理；
5. 不得自行合并、覆盖、迁移或推断当前事实源；
6. 历史文件保持原名，不因模板升级自动改名。

## 治理事件

允许的事件及建议编号如下：

| 事件类型 | 编号示例 | 产生方 |
|---|---|---|
| `GATE_DECISION` | `GATE-001` | 主智能体 / 运行时根据门禁决定登记 |
| `CANDIDATE_STATE` | `CAND-001` | 主智能体 / 运行时 |
| `WRITER_HANDOFF` | `WR-001` | 写入执行者 |
| `TEST_READINESS` | `TR-001` | 运行时 |
| `QA_RESULT` | `QA-001` | 临时质量验证 |
| `REVIEW_RESULT` | `RV-001` | 只读评审者 |
| `ROUTING_DECISION` | `RT-001` | 运行时自动规则或总控异常分类 |
| `HUMAN_RECOVERY` | `REC-001` | 主智能体 / 运行时根据人工证据登记 |
| `HUMAN_ACCEPTANCE` | `HA-001` | 主智能体 / 运行时根据人工事实登记 |
| `FACT_CORRECTION` | `COR-001` | 主智能体 / 运行时 |

事件编号只在当前 `RequirementId` 内唯一。每个治理事件 JSON 至少包含：

- `SchemaVersion`；
- `RequirementId`；
- `ContextPackVersion`；
- `RepairLineageRef`；
- `EventId`；
- `EventType`；
- `CreatedAt`；
- `Actor`；
- `CandidateRef`；
- `Payload`；
- `EvidenceRefs`；
- `SupersedesEventRef`；
- `RedactionState`。

不适用的必填字段使用 `null`，不得虚构。

### 角色结果时间

`QA_RESULT` 和 `REVIEW_RESULT` 的 Payload 必须包含 `StartedAt`、`CompletedAt` 和 `DurationMs`。时间使用包含时区的 RFC 3339；`CompletedAt` 不得早于 `StartedAt`，`DurationMs` 必须与二者差值一致，允许不超过 1000ms 的记录舍入误差。事件 `CreatedAt` 表示运行时持久化时间，不得早于 `CompletedAt`。

QA 中每个 `Disposition=EXECUTED` 的验证项也必须记录三项时间，且落在 QA 总区间内；`REUSED` 项不生成新耗时，只引用来源事件及原耗时。不得使用相邻事件的 `CreatedAt` 差推断命令执行时间、环境等待时间或角色耗时。

### 门禁决定事实

G1 与 G2 均使用 `GATE_DECISION` 不可变事件承载，不新增门禁 Markdown 记录。需求基线和开发上下文包继续保存人类可读的当前状态、依据与历史；`facts/gates/` 下的门禁事件是对应决定的机器事实源。

除治理事件通用字段外，每个 `GATE_DECISION` 的 `Payload` 至少包含：

- `Gate`：本轮门禁，使用 `G1` 或 `G2`；
- `ArtifactRef`：被判断的需求基线或开发上下文包稳定引用；
- `ArtifactVersion`：被判断产物的版本；
- `Decision`：G1 只允许 `CONFIRMED` 或 `REJECTED`；G2 只允许 `FROZEN` 或 `REJECTED`；
- `DecisionMode`：G1 使用 `HUMAN`；已形成决定的 G2 使用 `AUTOMATIC` 或 `HUMAN`；未决状态不产生事件；
- `BasisRefs`：支持决定的稳定事实引用；
- `ApprovalRef`：人工决定记录的稳定引用；自动决定时使用 `null`；
- `BlockingItems`：阻止通过或冻结的已有事实；没有阻塞项时使用空数组。

门禁输入、决定条件及执行许可唯一遵循[主流程的 G1、G2 与 UCR 边界](./多智能体协同开发治理流程.md#g1g2-与-ucr-边界)。机器绑定须满足：G1 绑定需求基线且 `DecisionMode=HUMAN`；任何 HUMAN 的 `ApprovalRef` 必须为非空稳定引用，AUTOMATIC G2 为 `null`；G2 的 `ArtifactVersion` 等于 `ContextPackVersion`。AUTOMATIC 只能 FROZEN，不能 REJECTED；未决不生成事件。仅已持久化的有效 G1 CONFIRMED 允许技术规划，仅有效 G2 FROZEN 及已冻结上下文包允许初始化记录。

门禁事件只记录已有决定，不由模板、运行时投影或下游角色反向生成审批结论。门禁决定有误时只能使用 `FACT_CORRECTION` 追加纠正；不得覆盖原事件、删除拒绝或阻塞历史，或把旧决定改绑到新产物版本。

### 写入交接与任务执行事实

“任务点”与开发上下文包中的工作包是同一概念，唯一标识统一使用 `WorkPackageId`。每个 `WRITER_HANDOFF` 必须绑定 `WorkPackageId`、`WriterRound` 和写入槽位，并在 `Payload.Changes` 中逐项记录实际代码修改事实。每个 `Changes` 条目至少包含：

- `ActionId`：当前写入交接内唯一；
- `Operation`：只允许 `ADD`、`MODIFY`、`DELETE`、`RENAME`、`MOVE`；
- `Path`：仓库相对文件路径；
- `CodeUnit`：模块、类、函数、方法、接口、配置项、数据结构、迁移对象或其他稳定语义定位；
- `Summary`：已经发生的修改事实；
- `Reason`：关联范围、契约、验收标准或任务完成条件；
- `EvidenceRefs`：完成敏感信息检查的稳定证据引用。

不得用完整 Git 差异、大段源码、内部推理或单独行号替代 `CodeUnit`。无法提供语义定位时，`CodeUnit` 使用文件级稳定对象并说明原因；行号只能作为辅助信息。没有实际修改时 `Changes` 使用空数组，不得虚构操作。

`WRITER_HANDOFF`、`CANDIDATE_STATE`、验证、评审和路由事件共同构成开发过程事实。运行时按 `WorkPackageId` 和轮次将这些事件投影到 `开发记录.md`，不得让 Markdown 自行产生任务状态或修改事实。

## 追加、纠错与幂等

已经持久化的事实事件（包括 `GATE_DECISION`）不得修改、覆盖或删除。事件内容有误时，追加 `FACT_CORRECTION`，并通过 `SupersedesEventRef` 指向被纠正事件；原事件必须保留。

运行时写入前必须同时核对 `EventId` 和内容摘要。相同事件已经存在时不得重复写入、重复计数或重复触发角色；编号相同但摘要不同属于冲突，必须停止。

## 结构与语义校验

计划契约和角色输出都不是一经返回就自动成为事实。v3.0 先校验 `ControlProfile` / `AcceptancePlan`；随后对实际角色输出按以下顺序校验，全部通过后才分配 / 确认事件编号并原子持久化：

1. 依据 `SchemaVersion` 校验 JSON 类型、必填字段、固定枚举和 `additionalProperties=false`；
2. 核验 `RequirementId`、`ContextPackVersion`、`RepairLineageRef`、`CandidateRef`、轮次和候选摘要绑定；
3. 核验有效验证集合或静态评审范围覆盖完整且没有重复 ID；
4. 核验 PASS / FAIL / BLOCKED、APPROVE / CHANGE 的状态不变量；
5. 核验复用来源存在、原结果为 PASS，且满足预定义复用规则和候选关系；
6. 核验角色级及验证项级时间不变量；
7. 执行敏感信息检查和必要脱敏；
8. 核验 `EventId`、轮次、幂等键和期望前序事件唯一性。

校验失败时只返回结构化 `ValidationErrors`，不得保存 `QA_RESULT` / `REVIEW_RESULT`、增加轮次或计数、生成路由或更新 Markdown；应要求同一角色轮次重新输出合格结构。写入使用临时文件加原子替换或等价原子机制，避免半写事件。由此发现的输出结构问题不得拖延到最终归档阶段再补造质量事实。

## 不可变候选

`CandidateRef` 必须引用 `facts/candidates/` 下的候选事实，不得只引用可变工作区路径。候选事实至少包含：

- `CandidateRef`、`RequirementId`、`ContextPackVersion` 和 `RepairLineageRef`；
- 基线提交 SHA；
- 候选提交 SHA，未提交时使用 `null`；
- 差异快照引用及摘要哈希；
- 变更文件清单；
- 未跟踪交付文件清单及摘要哈希；
- 写入执行者交接引用；
- 创建时间和工作区 / 工作树引用。

临时质量验证和只读评审开始前必须核对候选摘要。摘要不一致时不得继续使用原 `CandidateRef`。

## 测试就绪与增量复验

运行时派发临时质量验证前，必须依据开发上下文包对本轮 `Trigger=TRUE`、`Owner=QA` 项逐个执行 `TEST_READINESS`。该检查只核验候选绑定、命令定义、环境依赖、权限、工具、服务入口和上下文包声明的前置条件，不执行测试。每个就绪条目必须绑定唯一 `ValidationId`，并记录 `GateClass`、`GateTarget`、`AffectedWorkPackages`、`Readiness=READY / NOT_READY`、检查事实及证据引用；不得只用一个总体状态掩盖逐项差异。

- 至少一个项目为 `READY` 时即可创建 `QARound` 并派发 QA 先执行就绪项；若同时存在未就绪项，测试就绪总体状态使用 `PARTIALLY_READY`；
- 没有任何项目可执行且至少一个已触发 `BLOCKING` 项为 `NOT_READY` 时，保存 `TEST_READINESS/WAITING_FOR_TEST_PREREQUISITE`，并按 `ROUTE-000` 保存等待处置；不得创建 `QA_RESULT`、增加 `QARound` 或计入质量失败；
- 仅有 `ADVISORY` 项未就绪时不得进入等待；没有 `READY` 项且全部未就绪项均为 `ADVISORY` 时，仍可创建只记录 `NotExecuted` 的 QA 轮次而不执行验证命令，这些项目不阻止整体 `PASS`；
- 每个未就绪的 `BLOCKING` 项必须包含固定 `BlockerType`、责任方、客观恢复条件和证据引用；
- 相同候选、相同逐项阻塞且没有新的解除证据时视为同一等待状态，不得重复派发 QA 或重复生成等待路由；
- 阻塞解除后以新的逐项 `TEST_READINESS` 事实引用解除证据；至少一个项目成为 `READY` 后即可派发 QA。

同一候选的阻塞恢复或局部重验由运行时形成 `RevalidationPlan`，至少包含 `PlanId`、`TriggerQAEventRef`、`CandidateRef`、`ExecuteValidationIds`、合法复用项及来源事件、复用依据和失效原因。此前同一候选的 `PASS` 仅在开发上下文包预定义的复用规则满足时使用 `Disposition=REUSED`；其余已执行项目使用 `EXECUTED`。任何结果均不得跨 `CandidateRef` 复用；新候选必须重新执行其有效验证集合。`FAIL` 不得作为最终通过结果复用。

每个 `QA_RESULT` 必须覆盖当前完整有效验证集合，而不是只返回本轮新执行项。完整有效验证集合严格定义为 `EffectiveValidationSet` 与 `NotExecuted` 的并集：`EffectiveValidationSet` 只包含本轮 `Disposition=EXECUTED` 或同一候选合法 `REUSED` 的项目；`NotExecuted` 只包含已触发、归属 QA 但本轮未执行的项目。复用项必须引用原 `QA_RESULT`；`Trigger=FALSE` 或其他 Owner 的项目不属于该集合，也不得记为 `NotExecuted`。

### QA 结果不变量

`QA_RESULT.Payload` 至少包含 `ValidationPlanRef`、可选 `RevalidationPlanRef`、`EffectiveValidationSet`、`NotExecuted`、时间字段、`Status`、`BlockingItems`、`ObservedFailures`、敏感证据状态和 `GovernanceImpact`；完整性按前述两个集合的并集校验。

- 存在可可靠归因于候选的确定失败时为 `FAIL`，`ObservedFailures` 非空；即使其他项目受阻也保留其阻塞事实；
- 不存在确定候选失败，但至少一个已触发 `BLOCKING` 项无法可靠完成时为 `BLOCKED`，`BlockingItems` 非空；
- 其余情况下，候选摘要核验通过、所有已触发 `BLOCKING` 项以实际执行或合法复用得到 `PASS`，且不存在待脱敏证据问题，才可形成整体 `PASS`；
- `ADVISORY` 未执行不阻止整体 PASS，但其中实际发现的候选缺陷仍形成 FAIL；
- `NotExecuted` 只能记录已触发但未执行的项目；其中未执行的 `BLOCKING` 项必须由某个阻塞项覆盖，未执行的 `ADVISORY` 项只需记录客观原因和就绪事实引用，不得据此形成整体 `BLOCKED`。

每个阻塞项必须包含 `BlockerId`、固定枚举 `BlockerType`、`AffectedValidationIds`、`ResponsibleParty`、`Retryable`、`ResumeCondition`、`Fact` 和 `EvidenceRefs`。`BlockerType` 只允许候选绑定不一致、必要输入缺失 / 冲突、验证定义无效、环境 / 权限 / 工具 / 依赖 / 外部服务不可用、安全约束或证据待脱敏对应的协议枚举；不得使用自由文本类别。治理边界变化只通过 `GovernanceImpact` 表达。

### Reviewer 结果不变量

STANDARD / CONTROLLED 中实际触发的 `REVIEW_RESULT.Payload.ReviewScope` 固定为 `STATIC_CANDIDATE`。Reviewer 只依据当前候选、写入交接、冻结上下文包和适用规则判断静态实现、边界、契约、风险与测试源码充分性，不等待、读取或重判 QA 动态结果。`APPROVE` 只表示静态审查通过；当 AcceptancePlan 同时触发 QA 与 Reviewer 时，只有运行时与同一候选 QA `PASS` 汇合后才可进入人工验收。LEAN 不创建 REVIEW_RESULT。

`QA_RESULT` 与 `REVIEW_RESULT` 由角色形成原始质量结论；角色不得自行判断结果是否迟到。运行时必须在校验原始结果并持久化事件的同一原子步骤中，依据当时已存在的候选处置向 `Payload` 注入两个控制字段：`DispositionRef` 在候选尚无终结处置时为 `null`，迟到结果必须引用已有终结路由；`CountDisposition` 只允许 `ACTIVE` 或 `IGNORED_DUE_TO_PRIOR_DISPOSITION`。迟到结果不得改变角色原始结论，但其 `CountDisposition` 必须为后者，且不得改变连续计数或触发新路由。

## 质量汇合与路由事实

新需求的正常质量路由由运行时依据当前治理版本的 `ROUTE-*` 规则机械生成；总控编排器只处理 `EXCEPTION_ROUTING`。每个 `ROUTING_DECISION` 除通用字段外至少包含：

- `DecisionMode`：`AUTOMATIC` 或 `ORCHESTRATED`；
- `RuleRef`：命中的稳定 `ROUTE-*`；异常分类时为 `null` 并提供 `ExceptionReason`；
- `TriggerEventRefs`：触发本次决定的一个或多个不可变事件引用；
- `JoinState`：`PENDING`、`COMPLETE` 或 `TERMINATED`；
- `Decision`、`Target`、`CounterState`、`GovernanceImpact`、`BlockingItems`；
- `DispositionRef`：当前候选已存在终结处置时的稳定引用，否则为 `null`。

在 STANDARD / CONTROLLED 同时触发 QA 与 Reviewer 时，单独收到 QA `PASS` 或 Reviewer `APPROVE` 只形成可从事件历史计算的 `JoinState=PENDING`，不创建路由事件。只有汇合完成、候选需要返回写入、进入前置等待、达到终止阈值或异常分类形成实际处置时才保存 `ROUTING_DECISION`。派发前没有任何 QA 项可执行且存在未就绪 `BLOCKING` 项时，以 `TEST_READINESS` 为触发事实，按 `ROUTE-000` 保存等待路由；已创建 QA 轮次后的 `BLOCKED` 使用 `ROUTE-004`。LEAN 第一阶段不使用本路由协议。

规则优先级、双失败合并、终结处置唯一性与等待恢复条件以[主流程路由表](./多智能体协同开发治理流程.md#候选质量汇合与路由)为准；持久化基于本次已保存的事件快照，不重判角色结论。迟到结果按上节原子注入处置控制字段，禁止重复计数或路由；可恢复等待不终结候选。

## 连续计数

### v3.0.1 增量规则：环境等待与同轮续跑

本节仅适用于明确绑定 v3.0.1 的新需求，不重新解释历史轮次。环境处理原则引用[测试规范](../开发规范/测试规范.md)的 `TST-009`～`TST-011`。

新版先按[治理修订说明](../治理版本说明/v3.0.1治理修订说明.md)区分 ObservedFailures.Attribution。仅 CANDIDATE 推导质量 FAIL；PREEXISTING/UNATTRIBUTED 保留实际失败，必要门禁仍未解决时 BLOCKED。归因不足的 BlockerType 使用 BASELINE_UNATTRIBUTABLE，不冒充 ENVIRONMENT_UNAVAILABLE；此类问题走受控调整或补充基线证据，不自动重启服务。历史事件的旧字段语义不改写。

运行时在 TEST_READINESS 阶段不能自主恢复环境时，向人工报告阻塞、已做尝试、责任方及解除条件，并停在等待状态。只有新解除证据才触发最小就绪复查；定时续行、重新创建角色、收到泛化“继续”均不重置自主恢复预算。没有任何可执行项时仍按 ROUTE-000 等待，不分配 QARound；已形成 QA BLOCKED 时仍按 ROUTE-004 等待。

同一候选、上下文版本、修复谱系和验证计划未变时，恢复复用原 QARound，分配新的 EventId，绝不覆盖旧 QA_RESULT。恢复事件的 Payload 增加 `ResumeQAEventRef`（本轮最近一条 BLOCKED 事件）与 `ResumeReadinessEventRef`（新就绪事件）；首个结果两者省略或为 null。新事件仍使用原 SchemaVersion v1.1 envelope 与机器 FactProtocolVersion v2.1；扩展是否适用由上下文文档 v3.0.1 绑定区分。

同轮恢复校验必须满足：

- 前序事件为 ACTIVE/BLOCKED，引用同一候选、上下文、谱系、QARound 和 ValidationPlanRef，不允许从 FAIL/PASS 或已终结处置继续；
- 新 TEST_READINESS 晚于被恢复的 BLOCKED 且不晚于恢复执行开始，至少有一个原受阻验证变为 READY，并引用可定位的解除证据；人工表示“已修复”不替代就绪检查；
- 保存 RevalidationPlanRef，完整有效验证集合保持不变，每个实际新执行项均为 READY；合法复用的 PASS 保留 SourceQAEventRef，环境或命令变化使证据失效时重新执行；
- 若仍有未解除阻断项，继续保存本轮 BLOCKED，不新增逻辑轮次；无新解除证据时不追加重复事件；
- 计划或候选变化不能伪装为环境恢复。候选变化沿现行新候选规则执行，计划变化进入受控纠正。任何历史 FAIL 都不能以恢复标识消除；
- QA 的各次实际执行时间分别记录，人工等待时间留在事件间隔中，不计入实际验证耗时。复用项目不重复累计执行时间。

事件幂等与质量计数仍基于 EventId、内容摘要和 CountDisposition。BLOCKED 不计失败；最后有效 PASS 只归零一次；同一事件重复投递不重复路由。渲染器检查恢复引用、轮次、候选、计划、时间和逐项就绪绑定；它不是自动调度器，不代替运行时派发前的去重、计划合法性及证据摘要校验。

### 现行计数规则

连续计数是事件历史的计算结果，不是可独立编辑的事实：

- `QA_RESULT/PASS`：仅当 `CountDisposition=ACTIVE` 时，临时质量验证连续失败计数归零；
- `QA_RESULT/FAIL`：仅当 `CountDisposition=ACTIVE` 时，临时质量验证连续失败计数加一；
- `QA_RESULT/BLOCKED`：连续失败计数保持不变；环境、权限、工具、依赖、输入或证据阻塞不属于候选质量失败；
- `REVIEW_RESULT/APPROVE`：仅当 `CountDisposition=ACTIVE` 时，Reviewer 连续失败计数归零；
- `REVIEW_RESULT/CHANGE`：仅当 `CountDisposition=ACTIVE` 时，Reviewer 连续失败计数加一；
- 任一迟到结果的 `CountDisposition=IGNORED_DUE_TO_PRIOR_DISPOSITION`：两类计数均保持不变；
- 新的 `FROZEN ContextPackVersion` 建立新的计数作用域；
- `HUMAN_RECOVERY` 按已批准恢复事实建立新的计数起点。

`QARound` 随每个通过协议校验并成功持久化的 `QA_RESULT` 增加；`TEST_READINESS` 等待不占用轮次。连续失败达到终止阈值只统计 `FAIL`。Markdown 中的当前计数只是投影；不得把 `BLOCKED` 次数或等待时长混入质量失败计数。

## 持久化顺序与恢复

门禁阶段必须按以下顺序持久化：

1. 形成并保存需求基线；
2. 明确 G1 决定后，保存绑定该需求基线版本的 G1 `GATE_DECISION`；尚未形成决定时不产生事件；
3. 只有已保存的 G1 `CONFIRMED` 才允许开始技术规划并形成开发上下文包；
4. 明确 G2 决定后，保存绑定该开发上下文包版本的 G2 `GATE_DECISION`；尚未形成决定时不产生事件；
5. G2 `Decision=FROZEN` 保存后，将对应开发上下文包标记为 `FROZEN`；
6. 只有 G2 `FROZEN` 事件和已冻结上下文包均可核验后，才初始化开发记录。

相同门禁事件已经存在且内容一致时视为幂等完成，不得重复登记或再次触发决定；编号或产物绑定相同但内容冲突时必须停止。中断发生在门禁决定已保存、下游动作尚未开始时，恢复只能从该已保存决定继续，不得重新生成另一条决定。决定未保存或绑定无法核验时，不得凭 Markdown 当前状态越过门禁。

开发上下文包 G2 冻结且对应门禁事件已经持久化后，运行时必须按[开发记录模板](./开发记录模板.md)初始化当前需求的 `开发记录.md`，写入计划任务点并将状态设为 `IN_PROGRESS`。新需求不再生成 `需求索引.md`。

初始化时，运行时必须为本次目标分支交付分配需求迭代版本：读取同一 `RequirementId` 下既有开发记录和全局版本台账，取尚未使用的最小下一顺序 `VNNN`，并在写入前核对唯一键冲突。总控编排器、写入执行者和归档智能体不得自行生成或改号。中断恢复必须复用已经写入开发记录的迭代版本，不得重复分配。

写入执行阶段：

1. 保存不可变 `WRITER_HANDOFF`；
2. 按 `WorkPackageId` 和 `WriterRound` 形成开发记录待投影内容并排队刷新任务点总览、逐任务明细和代码修改事实；过程时间线只在关键状态跃迁时更新；
3. 建立并保存不可变 `CANDIDATE_STATE`；
4. 将候选引用加入开发记录的待投影内容，不等待 Markdown 写入即可继续；
5. 只有所有当前有效任务点均具有完成、经批准取消或替代事实时，才可将开发记录状态投影为 `IMPLEMENTED`。

候选质量阶段：

1. STANDARD / CONTROLLED 保存候选后在第一阶段启动 Reviewer 与 QA 就绪检查；LEAN 由 Writer 执行触发 RB/QG，不生成空角色事实；
2. 至少一个 QA 项 `READY` 时启动 QA；没有项目可执行且存在未就绪 `BLOCKING` 项时按 `ROUTE-000` 等待且不创建 QA 轮次；没有 `READY` 项且仅有未就绪 `ADVISORY` 项时，允许创建只记录 `NotExecuted` 的 QA 轮次；
3. 分别校验并原子保存 `QA_RESULT`、`REVIEW_RESULT`，再从事件历史计算各自失败计数；
4. 运行时按版本化规则判断是否需要等待另一结果、自动形成处置或调用 `EXCEPTION_ROUTING`；
5. 有实际处置时保存唯一 `ROUTING_DECISION`；单一 PASS / APPROVE 等待汇合时不补造路由；
6. 路由事实保存后即可启动获准的下一动作；运行时只为阶段 Markdown 和开发记录摘要排队异步投影，不在角色或路由关键路径同步写入。

若结果已经保存但应有的处置事件不存在，恢复时只重算汇合并补充路由，不得重新执行角色或重复计数。若投影失败，只重试或从事实重建投影，不回滚事实、不重复角色、不阻塞下一动作。任何步骤中断后都从最后一个已持久化事件恢复。

每份质量阶段 Markdown 和开发记录摘要必须显示 `ProjectionState`（`CURRENT` / `PENDING` / `STALE`）、`ProjectedThroughEventRef` 和 `ProjectedAt`。投影任务以最后事件游标幂等刷新；正常质量路径只在候选处置形成、进入人工验收、人工验收完成和最终归档等稳定边界刷新，时间线只投影关键状态跃迁，不为每个角色结果复制一行。角色、路由和中断恢复只消费已校验 JSON 事实，不依赖 Markdown 已经更新。最终归档冻结前必须执行一次投影追平与一致性核验；在此之前，单纯 `PENDING` / `STALE` 不属于候选质量失败或 QA 阻塞。

人工业务总验收通过后，开发溯源归档智能体核验并补齐同一份开发记录，将状态更新为 `ACCEPTED_PENDING_MERGE`。目标工程流程完成后，它补齐 MR / Commit 事实，向 `docs/需求版本管理.md` 追加唯一需求迭代记录，确认两处引用一致后再将开发记录冻结。任一步骤中断时只补未完成步骤，不得重复追加全局版本记录。

## 需求迭代版本与全局台账

需求迭代版本使用 `VNNN`，在同一 `RequirementId` 内从 `V001` 递增。它表示一次完成目标分支交付的开发迭代，与治理版本、模板版本、Markdown 产物版本和产品发布版本相互独立。

`docs/需求版本管理.md` 是跨需求的人类可读导航投影，不是机器事实源。唯一键为 `RequirementId + 需求迭代版本`。只有 MR 已合并或等价目标分支流程已完成，且提交人、提交时间、原始需求摘要、最终实现功能摘要、Commit / MR 事实和开发记录链接均可定位时，才能追加记录。

存在已合并 MR 时，提交人取 MR 作者，提交时间取实际合并时间；无 MR 且直接提交目标分支时，提交人取 `BusinessDeliveryCommit` 的提交者，提交时间取该 Commit 时间。时间必须使用包含时区的 ISO 8601 格式。相同唯一键和内容已经存在时不得重复写入；相同唯一键内容冲突时必须停止并依据可定位工程事实纠正。

## 敏感信息与证据

敏感信息保护优先于原样持久化。“原样”是指完成必要脱敏后，不改变角色结论、字段语义和非敏感事实。

不得持久化 API Key、Access Token、密码、私钥、Cookie、Session、数据库凭据、完整环境变量、完整 prompt，或包含上述内容的完整日志、命令和截图。

发现疑似敏感信息时：

1. 停止写入该证据；
2. 将证据状态标记为 `REDACTION_REQUIRED`；
3. 只记录证据类型和风险位置，不复制敏感值；
4. 脱敏后生成新的安全证据引用；
5. 不得在纠正事件中重新记录原始敏感值。

`RedactionState` 只允许 `SAFE`、`REDACTED`、`REDACTION_REQUIRED`。本机临时日志不得作为长期稳定引用；进入 Git 的证据必须是必要、最小且已完成敏感信息检查的内容。

## 证据位置与保留

- 非敏感事实 JSON 随对应需求目录进入版本控制，并至少保留至该需求及其开发记录完成最终冻结；
- `开发记录.md` 和 `docs/需求版本管理.md` 只保存必要事实摘要与稳定引用，不得替代或复制完整机器事实；
- 日志、报告和截图是否进入 Git 必须由当前开发上下文包逐项规定，未规定时不得进入 Git；
- 被 `.gitignore` 排除的本机文件、会话临时文件和可变 URL 不得作为唯一长期证据；
- 不能安全进入 Git 的证据只能引用组织批准的受控存储；引用必须包含访问边界、不可变标识和保留期限；
- 尚无受控存储或保留策略时，只保存完成脱敏的最小事实摘要，并将无法长期保留的证据缺口如实记为阻塞或残余风险；
- 外部证据到期、撤销或不可访问时，不得静默删除引用；必须追加纠正事件并更新受影响的当前状态投影。

## 只读检查与区块生成工具

[governance_tools.py](../../scripts/governance_tools.py) 使用 Python 3.12 标准库，无新增依赖：

- `python scripts/governance_tools.py check --repo .`：有限的文档结构、引用和 TOML 检查，不是完整治理或 Schema 审查。
- `python scripts/governance_tools.py render --requirement-dir <需求目录> --kind qa-index`：输出 QA 索引；`review-index` 输出评审索引；`changes` 输出修改事实表。

生成器只消费已校验、已持久化的现行事件，执行消费所需检查后向标准输出生成确定性区块，不回写、不创建事件、不计算路由或计数、不宣布生命周期状态。三种输出分别放入对应模板的既有表格；原维护者继续维护其余章节和投影游标。失败不得用空表掩盖，亦不得改写原始事实使其通过。旧版、不支持的纠错、绑定冲突或敏感信息问题不自动转换；支持的输入边界以脚本说明及测试为准。

文档修订版本与机器标识独立：本次补丁仍使用 `FactProtocolVersion=v2.1`；持久化 envelope 的 `SchemaVersion` 沿用既有结构标识（本工具支持 v1.1），不能据此把历史 v1.1 事件当作现行 v2.1 语义。工具不建立新的机器格式或替代运行时的完整校验。
