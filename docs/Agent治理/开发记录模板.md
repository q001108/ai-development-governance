# 开发记录模板

模板状态：`FROZEN`
模板版本：v3.0
生效日期：2026-09-16

> 对应产物：需求级 `开发记录.md`。
> 核心问题：这个需求计划了多少个任务点、每个任务点实际做了什么，以及本次需求最终如何完成？
> `开发记录.md` 在 G2 冻结后初始化，是单需求目录的人类可读入口；生命周期、写入责任和冻结条件唯一遵循[开发溯源归档规范](./开发溯源归档规范.md)。

## 记录规则

- 完整保留各节；LEAN 不创建空 QA/Reviewer 投影，但在导航和质量摘要中标 `N/A（Profile 未触发）`；不适用项标 `N/A`，缺失事实如实标明。
- 计划引用冻结上下文包，实际执行引用已校验事件；不重新定义范围、契约或归属，不将计划写成结果。
- 第2、3、4、5节分别展示当前快照、轮次过程、代码单元级事实和关键状态跃迁，不复制完整事实或日志。
- 生命周期与写入责任按[归档规范](./开发溯源归档规范.md)，投影和敏感证据按[事实协议](./治理运行时事实协议.md#持久化顺序与恢复)。质量和人工决定原样引用，不由模板生成。
- 第4节可用 `python scripts/governance_tools.py render --requirement-dir <需求目录> --kind changes` 生成表格；命令只输出区块，不能替代其他章节或宣布投影已追平。
- 不收录完整对话、内部推理、完整差异、日志、人员工时或 Token 统计；允许记录 Profile 预算、EstimatedMinutes 和脱敏 DurationMs 聚合。

> 必须交付事实以项目实际采用的目标工程流程为准，不要求所有项目必须使用 代码托管平台、MR 或线上部署。`BusinessDeliveryCommit` 由人工在本地完成、人工验收后创建，其中不能引用自身 SHA；后续独立 `ArchiveFactCommit` 只记录已经存在的 `BusinessDeliveryCommitSHA`。`ArchiveFactCommitSHA` 只能从 Git 元数据或再后续事实观察，不得写入自身树，也不得为写回任一 SHA 改写需求基线或已绑定摘要。存在已合并 MR 时，提交人和提交时间分别取 MR 作者与实际合并时间；无 MR 且直接提交目标分支时，分别取业务交付 Commit 的提交者与 Commit 时间。MR、CI、审批和合并字段仅在流程适用时填写；版本、发布和部署仅在实际发生且有稳定事实时记录。
