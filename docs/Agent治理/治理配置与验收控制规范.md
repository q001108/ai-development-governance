# 治理配置与验收控制规范

状态：`FROZEN`
版本：v3.0
生效日期：2026-09-16

## 1. 目的与适用边界

本文定义 v3.0 第一阶段的统一 `GovernanceProfile`、确定性判级、控制事项分类、精简执行边界以及 `ControlProfile` / `AcceptancePlan` 机器契约。它不实现完整事件状态机、自动路由、跨候选证据复用、CI 流程改造或历史需求迁移。

v3.0 仅适用于生效后新建并显式声明 `GovernanceVersion=v3.0` 的需求。v2.1.1 及更早需求继续按各自产物中记录的版本解释；不得修改其历史基线、上下文包、事实或验收记录来模拟迁移。

## 2. 统一 GovernanceProfile

`GovernanceProfile` 只允许以下三个值，强度从低到高为 `LEAN < STANDARD < CONTROLLED`：

| Profile | 适用目的 | 默认角色边界 | Git 版本化记录 | 候选验证边界 | 时间预算 |
|---|---|---|---|---|---|
| `LEAN` | 单一、局部、可回退且无受保护面的小改动 | 主智能体/运行时、1 个 Writer；不默认调用独立 QA、Reviewer 或总控异常角色 | `需求基线.md`、`control-profile.json`、`acceptance-plan.json`、轻量 `开发上下文包.md`、`开发记录.md` | Writer 执行所有触发的 RB/QG；BA 由用户/业务验收方判断；AD 不阻断但单列成本 | 规划 ≤ 5 分钟，实施+RB/QG ≤ 20 分钟，等待外部/人工时间和 AD 成本另计；预计超出则升级 `STANDARD` |
| `STANDARD` | 普通产品开发、多个直接影响或需要独立质量判断 | 运行时、总控规划、Writer、独立 QA 与 Reviewer（第一阶段沿用双结果路由） | v2.1.1 五份记录职责继续适用，并新增两个 JSON | 触发的 BA/RB/QG 必须完成；AD 不阻断 | 按控制项估算，不设 LEAN 上限 |
| `CONTROLLED` | 受保护面、高影响、不可逆或外部交付风险 | 运行时、总控、Writer、独立 QA、独立 Reviewer、人工 G2 与业务验收；交付门禁按组织职责执行 | STANDARD 全部记录及受保护面决定/审批事实 | 触发的 BA/RB/QG 全部阻断；AD 仍不阻断，除非经正式变更重分类 | 控制项在计划中估算；审批、环境与交付成本由发生时的审批/交付事实记录，不设 LEAN 上限 |

“不默认调用”不等于禁止调用；一旦新增角色或控制成本使 LEAN 条件不再成立，必须先升级，不得在 LEAN 下复制 STANDARD 流程。

## 3. 确定性判级

### 3.1 固定求值顺序

运行时必须在 G1 后的技术只读审计中按以下顺序求值，并把所有实际命中项写入 `ControlProfile.Classification`。初次求值给出规划下限；DRAFT 上下文包、ControlProfile 与 AcceptancePlan 协同补齐工作包、控制和预算后必须按同一顺序重新求值，最终一致并校验通过才可进入 G2：

1. 先按固定枚举检查 `CONTROLLED` 硬触发器；命中任一项即锁定最低为 `CONTROLLED`，但仍完整记录较低档信号以保持契约闭集。
2. 未命中硬触发器时检查 `STANDARD` 升级条件；命中任一项即为 `STANDARD`。
3. 只有所有硬触发器和升级条件均已得到 `false` 证据，且全部 LEAN 资格条件为 `true`，才可判为 `LEAN`。
4. 任一必要事实为未知、缺失或冲突时，不得按 LEAN；至少判为 `STANDARD`。若未知项可能命中硬触发器，判为 `CONTROLLED`，直到证据解除。

不得以文件数量、用户称谓“简单”、时间压力、已有实现接近完成、测试通过或智能体主观低风险覆盖本顺序。

### 3.2 CONTROLLED 硬触发器

`HardTriggerCode` 只允许：

- `SECURITY_AUTH_PRIVACY`：认证、授权、密钥、隐私、敏感数据或安全控制；
- `REGULATED_LEGAL_FINANCIAL`：监管、法律、财务记账或资金行为；
- `DESTRUCTIVE_OR_IRREVERSIBLE`：不可逆操作、破坏性迁移或持久数据删除；
- `PRODUCTION_RELEASE`：生产部署、正式发布、远端强制操作或生产配置；
- `BREAKING_SHARED_CONTRACT`：公共 API、事件、数据格式或跨团队共享契约的破坏性变化；
- `PROTECTED_DATA_MIGRATION`：数据库模型、已发布迁移或生产数据迁移；
- `USER_MANDATED_CONTROLLED`：用户或正式业务契约明确要求 CONTROLLED、强制审批或独立审计。

### 3.3 STANDARD 升级条件

`UpgradeTriggerCode` 只允许：

- `MULTIPLE_WORK_PACKAGES`：需要两个及以上非机械拆分的工作包；
- `SHARED_CONTRACT_NON_BREAKING`：新增或修改非破坏性的公共/共享契约；
- `CROSS_MODULE_OR_TEAM`：跨产品模块、仓库或团队协作；
- `EXTERNAL_INTEGRATION`：外部服务、真实凭据、网络或第三方环境参与验证；
- `INDEPENDENT_QUALITY_JUDGMENT`：阻断结论不能由确定性命令给出，需要独立 QA/Reviewer 专业判断；
- `LEAN_BUDGET_EXCEEDED`：预计主动处理时间超过 LEAN 的“规划 5 分钟 + 实施及触发 RB/QG 20 分钟”预算；
- `LEAN_QUALIFICATION_FAILED`：任一 LEAN 资格条件不满足；
- `UNKNOWN_NON_PROTECTED_FACT`：必要事实未知，但已有证据排除 CONTROLLED 硬触发器；
- `USER_MANDATED_STANDARD`：用户或正式契约明确要求 STANDARD 或独立质量角色。

LEAN 资格条件固定为：单一工作包；改动局部且可回退；不涉及共享契约、受保护面、外部服务、数据库、CI/CD 或生产；所有阻断 RB/QG 都可由当前本地环境中的确定性命令或断言完成；触发且阻断的 RB/QG 与独立 `RiskTargetId` 均最多 8 个；每项只能绑定一个原子风险目标，RiskTargetId 不得复用，命令不得用 `&&`、`;`、`||` 或换行合并无关检查；主动处理时间不超预算；不存在需要产品/业务取舍的未知项。

### 3.4 升级与禁止降级

- 执行中出现更高档触发器时，必须在越界写入或继续验证前升级并生成新的 `ControlProfile` / `AcceptancePlan` 版本；已经发生的记录只追加引用，不覆盖。
- `CONTROLLED` 硬触发器只能由可定位的新事实证明“不再适用”，并经原决定责任等级确认后解除；不得由 Writer、QA、Reviewer 或成本考虑自行降级。
- 用户/正式契约指定的最低 Profile、人工批准要求、BA 来源、已触发的阻断 BA/RB/QG、受保护面和未解决未知项均是禁止降级边界。
- v3.0 第一阶段校验器不自动批准任何降级。初版固定为 `ProfileVersion=v1.0 / PreviousProfileRef=null / PreviousProfileRevision=null`；任何后续版本必须以 `PreviousProfileRef` 和完整 `PreviousProfileRevision` 绑定 HEAD 中实际生效的前一版，新 Profile 只能同级或升级且版本号严格递增。固定 `control-profile.json` 发生语义变化时不得挑选旁支伪前驱；校验器从该 Git revision 读取前版并递归核验。未来阶段若实现降级，仍只能发生在尚未产生候选时，并须加入原责任等级批准、旧控制保留与稳定证据校验；已有候选永远不得通过降级逃避既定门禁。

## 4. 控制事项分类

| 类别 | 含义 | 允许来源 | 默认责任方 | 是否阻断 |
|---|---|---|---|---|
| `BA` | 用户可观察的业务验收结果 | 仅用户明确需求或正式业务契约 | `HUMAN_ACCEPTANCE` | 是 |
| `RB` | 为保持既有行为而设的直接回归边界 | 已确认范围/契约、现有行为证据或风险 | `WRITER` / `QA` / `REVIEWER` | 触发时是 |
| `QG` | 可由确定性命令或机械断言判定的质量门禁 | Profile、项目规则、风险或明确用户验证要求 | `WRITER` / `QA` | 触发时是 |
| `AD` | 有价值但不影响当前候选放行的建议检查 | 规则、经验、环境能力或后续交付建议 | 任一明确 Owner | 否 |

### 4.1 BA 防膨胀规则

1. `BA` 必须逐项引用 `ControlProfile.BusinessAcceptanceSources` 中的 `BAS-*`。`AcceptancePlan.Statement` 与来源 `AcceptanceText` 按 Unicode NFKC、明确移除 U+200B ZERO WIDTH SPACE 与 U+FEFF、重复空白折叠、首尾空白及末尾中英文句读归一后必须相等；同一等价业务句不得因这些既定干扰字符或 Unicode 表示差异重复登记。不得笼统删除全部 Unicode `Cf`：U+2060 WORD JOINER、U+200D ZWJ 与 U+200C ZWNJ 均保留，避免吞掉排版、文字或 Emoji 可见语义差异。
2. `BusinessAcceptanceSources.SourceKind` 只允许 `USER_REQUIREMENT` 或 `FORMAL_BUSINESS_CONTRACT`，并必须提供稳定 `SourceRef`、`ApprovalRef`、`SourceArtifactVersion`、`SourceDigest` 与 `ApprovalDigest`。`ProvenanceRevision` 只是可选的来源快照 revision：为 null 时校验器读取工作区固定路径并核对两个 SHA-256 摘要，非空时从该 revision 读取并核对相同摘要；它不是业务交付 Commit SHA。人工验收后由人工创建 `BusinessDeliveryCommit`，其中可包含摘要绑定产物，但该提交及需求基线不得引用自身 SHA。随后只能在独立的 `ArchiveFactCommit` 中记录已存在的 `BusinessDeliveryCommitSHA`；`ArchiveFactCommitSHA` 从 Git 元数据或再后续事实观察，不得写入自身树，也不得为写入任一 SHA 改写需求基线或其已绑定摘要。G1、G2、规划、实施或验证中间阶段不得为满足校验而自动提交。用户需求的来源文本必须实际存在于当前 Requirement 的需求基线，ApprovalRef 必须指向同一 Requirement、同一产物版本的 G1 `CONFIRMED` 事实；基线正文实际产物版本、G1 `ArtifactVersion` 与 `SourceArtifactVersion` 必须三方相等。正式业务契约必须位于组织业务契约目录或当前需求的 `contracts/`，并由人工批准事实绑定。
3. 技术规范、RuleId、实现选择、文件路径、类/函数、库/框架、缩进/MIME/资源释放等技术细节以及 ESLint、类型检查、单元测试、浏览器方法等验证方法，不得直接生成 BA。它们只能进入 RB、QG 或 AD；只有用户/正式业务契约本身明确写入同一结果时，才可按原文作为 BA。
4. BA 不允许 `Method`、`Command`、`RuleId`、`RiskRef` 或技术 Owner。任一 BA 无来源、来源类型不合法、文本不一致、重复消费同一 `BAS-*`，或者混入禁止字段时，整个 `AcceptancePlan` 校验失败，不得冻结或开始实施。
5. 一个明确业务结果原则上对应一个 `BAS-*` 和一个 BA；拆分只允许来源本身明确包含可独立判断的多个结果，且必须先在 `BusinessAcceptanceSources` 中分别登记，不得由技术规划者自行拆分扩张。

## 5. LEAN 执行规则

LEAN 固定采用以下精简路径：需求基线 → G1 明确确认并持久化摘要绑定事实 → 技术只读审计 → DRAFT `ControlProfile` / `AcceptancePlan` / 轻量上下文包协同收敛 → 重新判级并校验 → 按计划要求形成 G2 决定 → 单 Writer 实施 → Writer 执行触发 RB/QG → 人工按 BA 验收 → 更新同一开发记录 → 人工授权业务交付提交。中间阶段不依赖 Git commit；用户要求实施不等于 G1 或 BA 通过。

第一阶段尚未实现 LEAN 自动状态机：Writer 必须在既有交接的证据引用中逐项标识对应 `ControlId`、命令退出码和脱敏结果，运行时人工核对 AcceptancePlan 的完整覆盖后才可进入 BA；不得生成 `ROUTE-*` 或声称自动 `VERIFIED`。后续状态机阶段应把该结果升级为独立机器事件，但不能据此回填或改写本阶段历史事实。

- 角色：运行时职责由主智能体承担；只允许 1 个 Writer。QG 能机械执行，因此不默认启动独立 QA；AD 不得触发角色。需要独立判断即升级 STANDARD。
- 记录：所有需求都必须进入 Git 版本化记录。`RecordRefs` 是全生命周期计划路径，不要求后置产物在 G2 前提前存在；冻结前只检查需求基线、两份 JSON 与 DRAFT 上下文包。LEAN 最小固定产物共五份：需求基线、`control-profile.json`、`acceptance-plan.json`、开发上下文包，以及 G2 后创建的 `开发记录.md`；事件 JSON 只在实际发生相应决定/候选/验收时记录，不为未发生角色制造空记录。不得只保留聊天、临时文件或 `.playwright-cli/`。
- 验证：所有 `Triggered=true` 的 RB/QG 必须有结果才能提交人工 BA；AD 可执行但不影响放行。机械命令失败必须修复或升级，不能改为 AD。
- 原子性：校验器以 `(Class, 归一化 Statement)` 形成不含 `ControlId`、`RiskTargetId`、成本和方法的机器指纹，拒绝 RB/QG/AD 重复陈述；同类、触发且阻断的 RB/QG 若均为 `COMMAND`，还按 Method 的 Unicode NFKC 与空白折叠结果拒绝复用同一命令，不能靠改写 Statement、ID、RiskTargetId 或预算伪拆分。LEAN 的 `COMMAND` 与 `DETERMINISTIC_ASSERTION` 另拒绝 `&&`、`||`、半角/全角分号和换行等显式多动作分隔符。机器不推断自然语言同义或命令语义，也不能可靠理解自然语言断言是否暗含多个无关检查；只要存在触发的 `DETERMINISTIC_ASSERTION`，校验结果必须给出 `RequiredG2DecisionMode=HUMAN`，由人工确认每项只对应一个风险目标。无法确认时必须升级 STANDARD，不得宣称自动原子性保证。
- 时间：规划预算 5 分钟，实施与触发 RB/QG 合计 20 分钟；`ImplementationMinutes` 与各控制项成本分别估算后相加校验，外部等待和用户响应单独记录。规划时预计超限直接 STANDARD，执行中确认超限则在下一越界动作前升级。时间预算不是跳过必要控制的理由。

## 6. 结构化数据契约

v3.0.1 增量定义于[治理修订说明](../治理版本说明/v3.0.1治理修订说明.md)。明确绑定新版的契约使用匹配的 v3.0.1 版本字段、兼容开发者 ID，并在 ControlProfile 中绑定 BaselineBindings；原 v3.0 契约不补字段。冻结验证调整使用独立摘要绑定的调整记录，原文件的全字段保留规则继续适用，不通过放宽修订链删除阻断控制。本文以下 v3.0 字段说明是历史兼容规则，不能据此拒绝明确绑定新版的合法增量字段。

规范 Schema 位于 `docs/Agent治理/contracts/`。新需求文件固定命名为 `control-profile.json` 与 `acceptance-plan.json`；两者使用 UTF-8、唯一 JSON key、`additionalProperties=false`，并在冻结前执行：

```powershell
python scripts/governance_tools.py validate-plan --control-profile <path> --acceptance-plan <path>
```

默认 `--mode live`，两份 JSON 必须位于 `docs/requirements/<RequirementId>/` 的固定路径，返回机器 JSON `Mode=LIVE / G2Eligible=true`。历史样本分析必须显式使用 `--mode replay`，且只允许 `docs/Agent治理/replays/<RequirementId>-v3/`，返回 `Mode=REPLAY / G2Eligible=false`。G2 入口必须使用独立 `validate-g2` 命令；`validate-plan` 的成功退出码本身不是 G2 凭据。

校验器在 Python 语义校验前，使用标准库实现的 Draft 2020-12 子集对 Schema 实例进行校验，覆盖本目录 Schema 实际使用的 `$ref`、类型、常量/枚举、正则、对象字段、数组、数值下限与条件分支。Schema 不能表达的触发器枚举完整性与唯一性、跨文件引用和摘要/版本绑定、计算后 Profile、聚合计数与成本、归一化 BA 等价、控制语义指纹唯一性以及回放报告一致性，继续由 Python 语义校验器负责；不得把 Schema 通过单独当作计划有效。

### 6.1 ControlProfile

关键不变量：

- `SchemaVersion`、`GovernanceVersion` 和 `DecisionRulesVersion` 均为 `v3.0`；
- `RequirementId` 必须匹配 `REQ-YYYYMMDD-NNN`，两个文件必须一致；
- `SelectedProfile` 必须等于按第 3 节从 `HardTriggers`、`UpgradeTriggers`、`LeanQualifications` 机械计算的结果；
- 每个触发器枚举最多出现一次，命中项必须有非空 `EvidenceRefs`；所有 LEAN 资格必须逐项给出布尔结果与证据，不允许缺项；
- `MinimumProfile` 是用户/正式契约指定下限，最终 Profile 不得低于它；初版必须为 v1.0/null/null，后续版必须用引用与 Git revision 绑定 HEAD 前版、严格提高版本号且不得降级；
- BA 来源 ID 唯一，且同一 Requirement 内语义等价规范化后的 `AcceptanceText` 不得重复；来源文件、批准事实、摘要、三方产物版本和可选最终 revision 必须相互匹配；正式业务契约批准结构须绑定 `ContractRef` / `ContractVersion`；
- `RecordRefs` 声明全生命周期计划路径；G2 前只要求基线、两份计划 JSON 与 DRAFT 上下文包存在，开发记录及质量投影必须等相应阶段实际发生后才创建；
- LEAN 时工作包数、全部阻断 RB/QG 数、独立原子风险目标数、阻断成本与 AD 单列成本必须满足第 3.3、5 节。

### 6.2 AcceptancePlan

关键不变量：

- 每项 `ControlId` 前缀必须等于 `Class`，ID 在文件内唯一；
- `PlanVersion` 必须与 `ProfileVersion` 相等；初版使用 `PreviousPlanRef=null / PreviousPlanRevision=null`，后续版与 Profile 一起绑定 HEAD 前版并严格递增；第一阶段对前版已触发且阻断的 BA/RB/QG 执行全字段保留，不得删除、改写、取消触发、替换方法/Owner/平台或压低预算；升级所需的新责任项另增 ControlId；
- `Triggered=false` 的 RB/QG/AD 不进入执行集合；BA 必须 `Triggered=true`；
- BA 适用第 4.1 节全部规则，且 `Blocking=true`、`Owner=HUMAN_ACCEPTANCE`；
- 触发的 RB/QG 必须 `Blocking=true`，提供唯一 Owner、客观 `Method`、当前 Profile 声明的有效本地 `ExecutionPlatform`（`WINDOWS`、`MACOS` 或 `LINUX`）和至少一个来源引用，不得使用 `NONE`；非触发 RB/QG 及 BA 继续固定使用 `NONE`。`RULE:<RuleId>` 必须解析为规则定义表中的现有 RuleId，`PROFILE:` 必须等于当前 SelectedProfile，`RISK:` / `USER:` 后必须是可定位文件及锚点；QG 的 `Method` 必须是机械命令或确定性断言；RB/QG/AD 的同类归一化陈述不得重复，即使更换 ControlId、RiskTargetId、成本或方法也不能绕过；
- AD 必须 `Blocking=false`，失败或未执行不得改变候选结论；
- LEAN 只允许 `WRITER` 执行 RB/QG；全部触发阻断 RB/QG 与唯一 `RiskTargetId` 均最多 8 个，不允许以 QA/Reviewer 为 Owner；需要这些 Owner 时 Profile 必须升级；
- 触发的 RB/QG `EstimatedMinutes` 必须至少为 1，并与 `BlockingControlsMinutes` 求和一致；LEAN 的 `ImplementationMinutes + BlockingControlsMinutes` 不得超过 `ImplementationAndControlsMinutes`。触发 AD 也必须声明正数成本并汇总到 `AdvisoryMinutes`，但不参与放行。每个阻断控制只能绑定一个且不得重复的 `RiskTargetId`，禁止拆分复用或命令链合并规避数量。第一阶段不允许 CI/RELEASE_PIPELINE Owner 或 `LINUX_CI` 执行平台。

## 7. 平台与 Codex 桌面边界

- 接入项目可声明 Windows、macOS 或 Linux 为本地开发环境。命令必须按实际 shell/路径语法定义，单一平台的结果不得外推为其他平台通过。
- `DeliveryValidation` 与 `DeliveryValidationStatus` 必须反映接入项目真实交付平台和可用能力；没有交付验证时标记 `NOT_AVAILABLE`，不适用时同时使用 `NOT_APPLICABLE`。不得规划项目并不存在的 CI/RELEASE_PIPELINE 门禁。
- 平台特有行为必须产生平台特有 RB/QG；跨平台无差异的纯文档或解释器标准库检查不需要机械复制三遍。
- Codex 桌面多智能体是执行能力，不是治理事实源。主智能体承担运行时编号、版本、持久化与边界核验；子智能体只获得最小任务和授权。LEAN 不为并行而并行，只使用单 Writer；STANDARD/CONTROLLED 可并行只读分析与独立质量角色，但最多 2 个不重叠写入槽位。
- `.playwright-cli/`、浏览器 profile、截图、trace、下载和其他会话临时产物均不进入交付，除非当前 AcceptancePlan 明确把脱敏证据文件列为 Git 产物。

## 8. 版本兼容与阶段边界

v2.1.1 保持为上一兼容版本；已有效绑定旧版本的需求继续使用原版本。本规范的回放只产生分析报告，不修改任何历史产物或事实。第一阶段只提供判级、计划契约和校验器；既有事件状态机与 `ROUTE-*` 不扩展为按 Profile 自动路由，也不允许跨候选复用证据。
