# 统一启动与续接（开发候选）

项目接入并启用需求管理后，AI 收到实施请求先使用统一入口，向开发者展示项目、需求、执行模式、实际阶段和下一动作。开发者继续用自然语言表达目标，无需手工组织登记、模式检查、状态查询和总表刷新。启动由当前任务触发，不是打开目录后自动运行的后台服务，也不新增门禁、批准、角色派发或测试轮次。

## 一次调用，按证据选择需求

以下命令由 AI 调用；路径相对实际项目根。`start` 是项目运行器对 `governance_start` 的短入口。

```powershell
python .governance/run.py start --repo . --intent new --title <摘要> --instruction <明确实施请求> --request-key <本次请求的稳定键>
python .governance/run.py start --repo . --intent continue
python .governance/run.py start --repo . --intent continue --requirement-id <已选ID>
python .governance/run.py start --repo . --intent query
```

AI 根据明确意图选择 new、continue 或 query，不通过关键词猜测业务语义。纯讨论和只读任务使用 query，禁止先登记再查询。new 的 request-key 由调用 AI 为同一次实施请求生成并在重试时复用，开发者不填写；也可显式提供此前已取得的 RequirementId。启动先把预留 ID 写入被忽略的请求回执，再登记，部分执行失败后按原键重试不会额外创建需求；同键不同输入拒绝。缺少开发者标识时返回一次性配置动作，缺少请求键时返回 AI 应补齐的动作，均不创建需求。只有键和文本完全一致才视为重试，不按文本相似度合并业务目标。

continue/query 的定位证据按以下处理：

1. 显式 RequirementId 优先；历史排除需求和未绑定需求返回原入口/迁移缺项，不自动接管。
2. 当前分支名称包含完整需求编号时，可定位已登记且未结束的需求。
3. 本工作区此前由成功启动建立的本地关联，可定位同一分支的需求；detached HEAD 额外要求同一提交。
4. 分支与本地关联冲突、多个编号、或没有可靠关联时，返回可选需求；即使只有一条进行中需求也不自行选定。

关联位于 `.governance/local/startup/contexts/`，按分支隔离，绑定本工作区、管理批次和需求绑定摘要。它只是选择依据，不是正式事实；切换分支不会带入上一分支的任务。关联无效时明确报告。只读查询不创建关联、请求回执、运行目录、需求、总表或远端缓存，也不获取远端。未完成选择的调用不写入。

## 项目策略与真实阶段

项目可在 `.governance/project.json` 声明 Startup.ProjectName，以及已批准的直接开发分支；通用内核不包含公司业务名称或分支。例子中的分支必须替换成项目已有明确策略，不因声明入口而自动扩大授权：

```json
{
  "Startup": {
    "ProjectName": "Example",
    "DirectDevelopment": {
      "Branches": ["feature/approved-delivery"],
      "PolicyRef": "AGENTS.md",
      "Instruction": "沿用项目已明确的本次交付直接开发要求"
    }
  }
}
```

普通正式治理项目无需 DirectDevelopment。只匹配明确分支，不按 Git 祖先把豁免传播到 dev 或其他分支。隔离适配试验可显式增加 `IsolatedOriginRef=.governance/local/worktree-origin.json`，仅当 detached HEAD、记录用途为 ISOLATED_ADAPTER_TEST、来源分支被列明且实际提交与 BaseCommit 完全一致时适用；该本机记录不提交、不作为永久分支豁免。派生业务分支需要项目核验明确创建事实后配置，不能靠祖先猜测。

实施启动沿已有项目策略持久保存 MANUAL；query 只报告适用策略与当前需求实际模式，不替用户退出。已有明确 RESUME 不被分支默认策略强行改回 MANUAL。结束的迭代只展示结束状态，不自动 next、不启动测试。

统一入口是当前项目的路由器，已有需求的 inspect、status 和管理操作仍通过其 plugin-binding.json 选择原发行。升级默认插件不会把旧需求迁到新内核。当前默认发行缺少统一入口时需要正常升级预览与应用，不能直接修改锁定发行。门禁或事实无法可靠判定时返回 BLOCKED 和原缺项；READY 只表示启动上下文已定位，不是实施授权、质量通过或人工验收。

## 回执与后续执行

返回 Outcome、SelectionBasis、Requirement、ProjectPolicy、NextActions、Problems 和实际 Writes。向开发者只展示简短回执，例如“需求 / 模式 / 当前阶段 / 下一步 / 阻塞”，需要排查时才展示完整 JSON。

new/continue 完成定位后保存本地关联，并刷新总表；远端读取失败按已有缓存状态报告，刷新失败显示 PENDING，不撤销已保存的登记或接管指令。`--no-fetch` 用于离线或隔离验证。新建请求的 ID 回执用于失败恢复；重试必须复用原 request-key 或 RequirementId。

启动不执行测试或启动服务。AI 根据返回的当前阶段继续原流程：G1 前只处理基线；正式验证阶段沿原 B1 自动准备；MANUAL 沿项目普通验证规则执行。不需要开发者再说一次“先检查环境”，也不把一次启动检查当成稍后测试环境仍可用的证明。退出/恢复、交付及串行迭代继续使用[需求管理](需求管理.md)的原有命令和事实边界。
