# 需求管理增量协议 v1.0（开发候选）

状态：2026-10-29，项目明确采用后适用。本协议提供需求登记、阶段导航、串行迭代及开发者主动接管；RequirementTrackingVersion=v1.0 与治理、事实、模板及插件版本分别绑定。原 v3.0.2 规范正文和历史需求保持原绑定。公司仓接入和 Git 提交/推送另按授权执行。

## 内容归属与统计起点

社区插件维护通用模板与工具；项目维护配置、领域规则及业务事实。一次可独立验收的业务目标对应 RequirementId；对话、修复轮次和代码提交不自动变成新需求。实施请求进入登记，纯讨论、解释、检索和只读查询不登记。

项目接入后显式启用新管理批次。启用时保存已存在的需求 ID 排除集合，之后只接收新登记且绑定该 BatchId 的需求，不导入旧在途或已归档记录。该配置需要随人工上传，其他分支沿用同一个批次；不得各自启用不同批次后假定它们是一个总表。编号继续使用原开发者标识和预留规则，不能重用历史编号；不同机器或克隆的编号冲突必须报告。

```powershell
python .governance/run.py governance_requirements enable --repo . --remote origin --web-base https://gitlab.example.invalid/team/project/-/blob
python .governance/run.py governance_requirements init --repo . --title <需求名> --instruction <安全的原始需求文本>
```

WebBase 是固定提交浏览地址前缀：GitLab 通常为项目地址加 /-/blob，GitHub 为项目地址加 /blob；由项目配置声明，不猜测托管平台。无远端的隔离项目可不填 remote/web-base；没有可用 web-base 时，共享记录显示精确的 git show 命令而不生成指向可变工作树的错误链接。

`enable` 创建 .governance/tracking.json，只固定批次、启用日期、排除 ID、远端与浏览前缀。已有批次幂等使用；配置冲突不覆盖。项目同一次明确接入授权涵盖配置生成，不要求每条需求重新启用。

## 单需求产物与阶段初始化

```text
docs/需求管理总表.md                   自动生成的全生命周期总表
docs/需求版本管理.md                   原归档交付台账，保持既有职责
docs/requirements/<RequirementId>/
  plugin-binding.json                 原固定发行绑定
  tracking.json                       当前批次的不可变登记身份
  需求基线.md                         初始需求草稿，保留用户原始文本
  control-profile.json                G1 后按真实证据填写
  acceptance-plan.json                G1 后按真实证据填写
  开发上下文包.md                     G1 后形成 DRAFT，G2 后冻结
  开发记录.md                         G2 后初始化，作为当前迭代入口
  facts/                              原有治理事实，门禁和质量结论来源
  tracking/head.json                  管理记录游标
  tracking/events/                    追加式管理事件及原始指令
  tracking/view.json                  最近一次安全观察，供上传和汇总
  tracking/requests/                  后续串行迭代的独立草稿
```

管理事件单独保存 BEGIN、ASSIGN、EXIT、RESUME、DELIVERY、CLOSE，不向旧 facts 增加未知事件类型。事件使用前序摘要、连续序号和内容摘要文件名；重复、断链、孤立事件或冲突停止自动判断。运行目录互斥及原子游标更新减少并发冲突；崩溃后的不完整写入需检查恢复，不伪装为事务已成功。

登记只创建固定绑定、需求基线草稿和管理身份，不创建门禁或开发记录。需要稳定重复调用时携带已有 RequirementId；不同输入不能冒用同一个登记。未提供 ID 时使用原开发者/日期/序号规则，检查本机可见工作树及 refs，在被忽略的本工作树运行目录独占预留，避免沙箱写受保护的 .git。需要一次性配置开发者标识；不通过需求文本相似度猜测编号。独占预留只覆盖当前工作树，不宣称跨机器/并行工作树全局原子唯一；上传后的重复身份由总表报告冲突，不能静默合并。

G1 后可运行 prepare-planning 生成开发上下文包模板和两个结构明确但尚未填写的 JSON 草稿。未知值保留 null，工具不猜测 Profile、触发器、验收标准、测试命令或人类批准，草稿不能通过计划校验。第一迭代沿用原规范固定根路径；实际规划和审核继续由原角色执行。

```powershell
python .governance/run.py governance_requirements prepare-planning --repo . --requirement-id <ID>
python .governance/run.py governance_requirements initialize-record --repo . --requirement-id <ID>
```

initialize-record 必须先核验现有计划、FROZEN 上下文及当前 G2，之后才分配 V001/V002… 并从开发记录模板初始化工作包导航。已有正式记录必须身份与迭代一致，不覆盖其他内容；重复初始化复用原编号。G2 前总表显示“待分配”，不用提前分配交付版本来填满表格。

## 共享总表与只读查询

```powershell
python .governance/run.py governance_overview query --repo .
python .governance/run.py governance_overview refresh --repo .
```

query 不写文件、不获取远端，也不改变当前分支。refresh 更新本地观察与生成区，总表已有非工具内容时拒绝覆盖。管理命令执行后尝试刷新本地总表；投影失败标记 PENDING，不撤回已经保存的退出指令。

主智能体在实施任务开始、续接及关键交接时自动 refresh；纯只读任务使用 query。refresh 只下载指定远端的分支，写入被忽略的 .governance/local/overview-remotes 独占裸仓缓存，避免工作区沙箱写入受保护的业务 .git；不 checkout、merge、commit、push 或执行远端脚本。项目已有 remote-tracking refs 可作首次缓存读取来源，远端失败时如实标识缓存状态。

每行展示需求/迭代、摘要、当前阶段、下一动作、过程入口、来源分支/提交和最近观察。以 RequirementId+迭代为显示粒度；G2 前用内部轮次区分待分配行，不把它当正式 VNNN。分别统计独立需求数与显示行数，不把修复或提交次数计为需求数。

共享条目来自已上传的固定 Git 提交。早期链接基线，当前开发链接开发记录，结束迭代的链接固定到历史提交。本地变化单独标“未共享”或显示为本机观察，不冒充团队共享进度。分支观察须与该提交中的完整来源摘要匹配；来源已变则显示过期/无法判定。跨分支同一身份或管理链不一致时显示冲突，不按时间戳挑一个胜者。

**来源摘要匹配只证明观察输入一致，不证明投影内容或门禁已经获批。** 共享阶段明确标“上传观察”；完整质量、人工验收和最终归档仍以原事实及原运行时核验为准。本工具不会把 QA PASS、手填 FROZEN 或开发者完成声明转换成正式验收。未知事件、缺项或纠错仍可显示 UNDETERMINED；已有 B3 未支持的汇合和验收不冒充已经自动实现。

记录随人工提交/推送后才共享；项目需要保留登记及过程历史，删除未合并分支前应按公司规则保存相关管理记录。独立本机缓存不能替代团队长期保留策略。断网或无访问权限不会触发重复角色派发。

## 主动退出与恢复

用户明确要求当前需求退出时，主智能体先记录原始指令并停止该需求后续治理派发，取消能够取消的角色、清理本次环境，再按普通开发方式继续协助。权限、敏感信息和 Git 边界继续适用；不要求人填写原因才能退出。

```powershell
python .governance/run.py governance_requirements exit --repo . --requirement-id <ID> --instruction <明确退出指令>
python .governance/run.py governance_requirements resume --repo . --requirement-id <ID> --instruction <明确恢复指令> --review <当前代码与原计划差异核查摘要>
```

EXIT 只影响当前 RequirementId，跨会话及其后续迭代保持，直到明确 RESUME；项目其他需求不受影响。总表保留退出、最近可核验阶段及人工交付声明。运行器停止该需求的治理执行，B1 和候选采集的直接入口也检查模式，状态查询、管理操作和环境 stop 仍可使用。已存活的测试会话检查模式并结束；无法确认取消/清理时报告实际状态，不删除开发者代码。工具不保证能强制取消所有外部 AI 进程。

恢复先核对现有计划和实际变更；范围变化按原 G1/G2/UCR 规则处理。review 是可定位的工作摘要，不冒充机器已完成业务语义判断。恢复事件记录旧候选摘要；新候选及管理游标绑定使旧质量结果失效，未形成新候选前显示相应缺项。工具不因“恢复”而生成通过事实或复用旧质量结论。

delivery 命令保留开发者完成摘要，可附已存在的 commit/目标 ref 并核验祖先关系。人工接管状态下显示“人工交付声明”，不显示正式验收通过。

## 串行迭代与历史

```powershell
python .governance/run.py governance_requirements delivery --repo . --requirement-id <ID> --instruction <完成说明> --summary <实际结果>
python .governance/run.py governance_requirements close --repo . --requirement-id <ID> --instruction <明确结束指令> --outcome TERMINATED --summary <结果> --commit <已存在的记录提交>
python .governance/run.py governance_requirements next --repo . --requirement-id <ID> --title <下一轮名称> --instruction <下一轮需求>
```

close 接受 DELIVERY_RECORDED 或 TERMINATED。受治理的交付结束还核对现有开发记录 FROZEN 与旧台账登记的一致性；该核对不代替完整归档审核。人工接管的交付结束保持声明性质。当前需求根中的必要输入必须已被指定提交完整保存；工具不自动提交记录。

只有本轮明确结束后才开启下一轮。上一轮的代码/过程引用保留在不可变 Git 提交，原事实不移动、删除或覆盖。next 生成独立草稿并记录已有事实摘要；后续规划沿原有 Profile/Plan 版本链和 G1/G2/UCR 规则修订根目录，不允许靠“新迭代”重置已有风险控制、清空事实或绕过 B4 的历史前驱要求。已有根文件保持原样，新的上下文与新的 G2 保存后才初始化下一迭代开发记录；旧 G2 和旧候选不能作为新轮次依据。

本需求的插件绑定继续固定，串行迭代不自动迁移发行。不同需求可并行；同一需求分支发生并行冲突时明确处理，不自动合并多个执行链。既有需求、既有普通计划修订和完整自动续接不因此被宣称迁移或补齐。
