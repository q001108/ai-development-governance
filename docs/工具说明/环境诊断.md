# 只读环境诊断

状态：B1 开发候选；原显式清单诊断数据格式 v1.0，新增本地发现数据格式独立使用 DiscoveryProtocolVersion v1.0。本文说明可选工具，不修改已发布 v3.0.2 治理规则，不新增 G1/G2 或 QA 派发条件。

## 用途与边界

`scripts/governance_environment.py` 聚焦本地开发。默认直接发现项目已有配置和相关本地工具；需要核对明确的需求归属、路径、端口及逐项准备声明时，继续支持显式清单。服务器部署环境留待后续交付工作处理。

本轮 B1 已收敛为测试执行前的环境准备；自动启动、夹具准备、端口覆盖和清理使用独立的[本地测试准备入口](本地测试准备.md)。本文所述自动发现与显式清单模式保持只读，作为辅助诊断使用，不要求在开发流程中新增三个必经检查阶段。

工具不执行配置中的命令，不读取凭据内容，不联网、不探测服务、不扫描进程，也不安装、启动、停止或清理资源。现有 `.parallel/` 或其他项目环境脚本继续负责实际运行；此工具不接管它们，也没有自动导入其任意配置格式。

本机清单是诊断输入，不是新的项目事实源。应从项目现有配置与本次运行安排提供所需字段，保持来源可核对；工具输出不能反向覆盖项目配置、已冻结计划或事实事件。

## 辅助使用位置

B1 的主入口是本地测试执行前，执行与恢复使用[本地测试准备入口](本地测试准备.md)。本文工具只提供元数据发现和声明核对，可作为测试准备的辅助输入；首次接入项目时也可按需运行，不要求规划、写代码和测试各新增一道检查。规划中尚未落实的环境前提继续按原规则安排责任、客观完成条件和就绪检查。

本工具输出是诊断报告。它不保存正式 TEST_READINESS，不核验候选真实性，不决定 G2 或 QA 派发，不把本地工具存在视为验证通过。正式就绪仍由既有流程按当前候选、ValidationId 及实际检查证据判断。调用时机也不会自动触发后续动作。

## 默认自动发现：无需手填清单

从当前 Git 工作树根执行：

```powershell
python scripts/governance_environment.py --repo .
```

多模块项目可以限定当前操作目录，避免把无关模块的工具缺项带入本次诊断：

```powershell
python scripts/governance_environment.py --repo . --scope frontend
```

`--scope` 是仓内相对目录，示例中的 frontend 必须替换为真实目录。发现模式可以附带 `--requirement-id` 作报告标签，但不会据此证明分支或工作树属于该需求；RequirementBinding 保持 UNKNOWN。`--phase` / `--owner` 仅用于显式清单模式，在发现模式中提供会报输入错误。

发现使用当前工作树中 Git 跟踪及未忽略的未跟踪文件列表，去重并跳过已删除文件；不读取历史提交内容。排除 `.git`、`.codex`、`.agents`、node_modules、虚拟环境、vendor 及常见构建目录，拒绝越界路径、符号链接和 junction，不读取 `.env` 或凭据文件。

| 已支持的来源 | 自动提取或检查 | 保留的未知项 |
|---|---|---|
| package.json | engines 中 Node/npm 版本声明、scripts 入口引用；支持 npm/pnpm/yarn 的 packageManager 声明，或根据唯一相邻锁文件识别包管理工具；检查工具是否存在 | 不执行脚本，不判断复杂版本范围、devEngines 或安装是否完整；多个锁文件且无明确声明时不替开发者选包管理工具 |
| pom.xml | 识别 Maven 项目标记、Java/javac 存在性及同目录 Maven Wrapper 入口；无 Wrapper 时检查 mvn 存在性 | 不解析父 POM、profiles 或有效模型，不运行 Maven/Wrapper；Wrapper 存在不表示离线可用，Java/Maven 版本要求待项目实际核验 |
| pyproject.toml | project.requires-python 声明、project.scripts 入口引用，以及 PATH 中 python 存在性 | 不运行构建后端，不判断 Poetry 等工具专用配置、虚拟环境选择或依赖安装状态 |
| requirements.txt | 识别 Python 依赖文件标记及 python 存在性 | 不读取可能包含私有地址的依赖正文，不执行安装，不判断依赖是否已满足 |

报告区分声明值与实际存在性：DeclaredVersions 只来自文件声明，Tools 中 ExistsOnly=true 只表示本机能找到工具；DiagnosticInterpreterVersion 只是运行诊断工具的 Python 版本，不代表业务项目所用解释器。脚本仅输出入口引用，命令正文和工具绝对路径不进入报告。

结果使用 ResultType=LOCAL_ENVIRONMENT_DISCOVERY、Projects、Findings 和 Unverified。发现多个模块时 SelectionRequired=true，提示按实际任务选择；工具不会把所有模块都判为当前需求必需。没有支持的元数据时明确标注 NO_SUPPORTED_PROJECT_METADATA，不能推断项目已经就绪。首轮不自动检测数据库连接、端口占用、依赖完整性或工具版本兼容。

单份元数据上限 256 KiB，所选目录内最多 128 份，Git 列表上限 8 MiB。过大的、损坏的或含敏感信息而无法安全处理的受支持元数据，只报告来源与通用错误，不回显正文或解析异常。未知技术栈保留未知，不生成需另行手工维护的清单。

发现模式退出码：0 表示已完成发现且 Findings 为空，仍可能有 Unverified；1 表示存在缺工具、元数据无效或配置待确定等发现项，不代表治理阻断；2 表示 Git、路径、输入或读取边界导致无法完成发现。退出码 0 不能当作环境已就绪。

静态字段语义参考 npm CLI v10.9.9 的[package.json 文档](https://github.com/npm/cli/blob/v10.9.9/docs/lib/content/configuring-npm/package-json.md)。该文档版本仅为解析字段的参考，不表示项目使用该 npm 版本；不根据本机探测安装或升级任何依赖。

## 显式清单模式：继续兼容

从目标 Git 工作树执行，显式给出本机清单与本次需求标识：

```powershell
python scripts/governance_environment.py --repo . --manifest .parallel/governance-environment.local.json --requirement-id REQ-DEV-20261019-01 --phase planning --owner QA
```

准备真正执行验证前，可改用 `--phase execution`。`--owner` 默认为 `QA`，也可选择 `WRITER` 或 `REVIEWER`；只评估已触发且属于本次角色的验证前提。

清单应只留在本机或组织批准的位置，不能包含密码、Token、Cookie、连接凭据或完整环境变量。实际本机路径和运行参数不应随社区模板传播。清单本身须是工作树内的显式 JSON 文件，首期不支持共享目录、符号链接或外部路径资源。

## 清单格式

下例使用合成需求与占位根路径。`RepositoryRoot` 必须在本机替换为当前 Git 工作树的绝对根路径；不能把占位值当成实际环境。

```json
{
  "ToolProtocolVersion": "v1.0",
  "RequirementId": "REQ-DEV-20261019-01",
  "RepositoryRoot": "<当前 Git 工作树的本机绝对根路径>",
  "Paths": [
    {"PathId": "PROJECT_CONFIG", "Path": "README.md", "Kind": "FILE"}
  ],
  "Tools": [
    {"ToolId": "PYTHON", "Kind": "PATH", "Value": "python"}
  ],
  "Ports": [
    {"PortId": "BACKEND", "Port": 18080}
  ],
  "Validations": [
    {
      "ValidationId": "V-01",
      "Triggered": true,
      "Owner": "QA",
      "GateClass": "BLOCKING",
      "CommandRef": "project-test-command",
      "Prerequisites": [
        {
          "PrerequisiteId": "TEST_DATA",
          "Readiness": "PLANNED",
          "Responsible": "fixture-owner",
          "CompletionCondition": "isolated fixture available",
          "ReadinessCheck": "project-fixture-check"
        }
      ]
    }
  ]
}
```

| 字段 | 含义 |
|---|---|
| `ToolProtocolVersion` | 本诊断输入格式，固定 v1.0；不是治理或机器事实协议版本 |
| `RequirementId` | 当前诊断对象，必须与命令行一致；工具不分配编号、不证明其正式登记或批准 |
| `RepositoryRoot` | 清单声明的本机工作树根，必须与 `--repo` 指定的真实 Git 根一致 |
| `Paths` | 本次明确选择的全局资源；路径只能为仓内相对路径，`Kind` 为 FILE 或 DIRECTORY |
| `Tools` | PATH 工具只填写程序名，不带目录或参数；REPO_FILE 只检查仓内入口文件存在，不证明可执行或版本正确 |
| `Ports` | 本次声明的端口，检查范围与重复；不检查占用、监听进程、网络连通或服务归属 |
| `Validations` | 验证项 ID、触发状态、角色、阻断类别、命令引用与前提。引用只作标识，工具不执行它 |
| `Prerequisites` | 准备状态与责任、完成条件、检查引用；READY 也只是声明，不是已执行验证证据 |
| `CandidateRef` | 可选候选声明，不是候选真实性或服务对应关系的证明 |

各列表允许为空，但 ID 不允许重复。验证项的 `GateClass` 为 `BLOCKING` 或 `ADVISORY`；准备状态为 `READY`、`PLANNED` 或 `UNKNOWN`。

`Paths`、`Tools`、`Ports` 是本次显式选定的全局资源，不会根据验证项自动推导或从整个项目收集。请只列本次操作真正依赖的资源，避免把无关模块的准备成本带入诊断。

## 规划与执行的不同含义

规划阶段，具有明确责任方、客观完成条件及检查引用的 `PLANNED` 前提表示准备安排已描述。文件或工具尚不存在时记录未就绪情况，不由此工具自动判定 G2 失败；这也不表示实际环境已就绪。

执行阶段，本次角色已触发的阻断项仍为 `PLANNED` 或 `UNKNOWN` 时，报告必要前提未明。未触发、其他角色或建议项不因前提未就绪而变成本次阻断控制。全局资源缺失在执行阶段仍会报告，故清单应限定当前操作范围。

`READY` 统一视为声明值。没有外部观测或证据核验，不能据此宣称环境已满足正式 `TEST_READINESS`，也不能由 URL、端口或自报 `CandidateRef` 推断当前服务运行的是哪个候选。

## 输出与退出码

报告固定标明 `DiagnosticOnly=true`、`GatesChanged=false`、`QualityPassed=false`。`ServiceOwnership` 和 `CandidateBinding` 保持 `UNKNOWN`，供调用方看到仍需核实的边界。

`ReportChecks` 保存分项诊断，`BlockingIssues` 保存本次发现的问题，`Unverified` 保存声明、缺项与尚未核验内容。以上是诊断字段，不是既有事实协议中的 `Readiness`、QA 结果或门禁事件。工具不提供“可以派发”的批准结论。

| 退出码 | 含义 |
|---|---|
| 0 | 诊断处理完成，当前阶段没有发现须以非零退出报告的问题；仍可能有声明、PLANNED 与未核验内容 |
| 1 | 发现明确配置冲突，或执行阶段的所选必需资源/前提未满足 |
| 2 | 输入格式、路径安全、敏感信息检查或读取失败，无法完成诊断 |

退出码 0 不等于 G2Eligible、QA PASS、候选正确、服务可用或人工验收。正式门禁、逐项就绪事实及后续派发仍按原项目规则处理，本工具不写入任何事实或修改计数。

## 验证范围

工具测试使用临时 Git 仓库和合成配置，检查输入、误配、规划/执行差异、角色与建议项边界、只读和无命令执行。其他操作系统和真实项目环境的覆盖，以实际验证报告为准；不能由标准库实现推断全平台已经验证。
