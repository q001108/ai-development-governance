# 社区产品、插件发行与项目适配

状态：2026-10-28，C4/C5 已实现未发布开发候选，包括固定发行、项目接入/升级及实际运行器；独立 Codex CLI/app-server 已验证原生加载与 B1 自动调用，桌面 UI 及公司真实试用尚待验证。本文不改变已绑定的治理版本、事实契约或历史需求。

## 产品关系

社区仓是独立开发、验证和发布的产品源码仓；插件是从社区仓某个明确版本构建的可分发制品；公司项目是该产品的使用方，拥有自己的业务源码、项目配置、适配入口及治理事实。

“类与对象”可以帮助理解复用关系：社区维护通用能力，每个项目使用它并提供自己的参数与实现入口。实际版本管理采用固定版本依赖与组合适配；项目不是随社区工作区自动变化的内存对象，也不需要各自维护一份长期分叉的治理核心。

关系为：社区源码 → 固定版本插件 → 项目绑定与适配 → 实际需求执行 → 脱敏问题反馈 → 社区通用修复与新发行 → 项目显式升级。

## 内容归属

| 内容 | 正式维护位置 | 更新方式 |
|---|---|---|
| 通用治理规则、事实契约、校验与执行工具 | 社区产品源码仓 | 在社区修复并验证，形成新的产品发行 |
| Skill 入口、插件清单、规则包、分发资源 | 社区源码与构建制品 | 与对应发行版本一起固定，不在目标项目临时修改后冒充原版 |
| 项目架构、模块、领域约定、设计来源 | 公司项目仓 | 项目适配提交，引用项目自己的事实来源 |
| 本地启动、测试、夹具与资源隔离入口 | 公司项目仓 | 复用已有脚本，必要适配随业务项目独立验证 |
| 采用的插件版本、来源、内容摘要、选定规则包 | 公司项目的依赖锁定记录 | 升级时单独更新，能够回到原发行 |
| 需求、候选、测试、人工验收及交付事实 | 公司项目仓或组织批准的位置 | 继续作为本项目事实源，不回传社区 |
| 本机端口、路径、会话、凭据与运行数据 | 项目本机配置或批准的凭据设施 | 不进入社区、发行包或共享依赖锁定文件 |

社区仓本身作为普通产品项目维护。本轮已明确授权的体系自身优化继续采用直接审阅、实现和验证，不额外套 G1/G2/UCR；项目使用插件时仍按其已经绑定的治理规则工作。

## Skill 与插件的分工

Skill 负责能力发现、按阶段加载说明及调用确定性工具。治理判断所需的来源、候选、状态和安全检查仍由工具与既有事实规则承担；自动选用技能不等于机械门禁已经执行。

当前官方 OpenAI 文档支持用插件分发 skills 和其他资源。可移植插件以根 plugin.json 为入口，skills/ 包含 SKILL.md；Codex 兼容清单是另一种受支持格式。后续封装应按实际目标产品版本验证加载与安装，不同时维护两套重复清单。第一版采用技能入口与现有脚本、规则和文档资源即可。

社区源码中的发行入口已按以下结构创建，尚未发布：

```text
plugin.json
skills/development-governance/SKILL.md
scripts/
rulepacks/
docs/
```

SKILL.md 保持简短，按接入、规划、开发、测试与查询需要引用相应资源，通用规则正文只维护一份。插件资源路径必须相对发行根解析，业务路径相对项目根解析，两者不能混用。

## 项目适配与版本锁定

项目接入工具生成 .governance/project.json 和 .governance/plugin.lock.json，具体格式与调用见[项目接入与升级](项目接入与升级.md)。项目配置与锁定分别维护；锁定记录不包含开发者绝对安装路径。

项目入口引用已有配置，例如治理启用范围、governance.rules.json、package.json 中的本地测试入口及项目领域文档；不为此复制第二份命令、规则或需求状态。项目 AGENTS 保存短入口、项目约束和适配来源，避免每次升级都整文件覆盖。

锁定记录分别表达插件发行版本及内容摘要、社区来源提交、治理/测试规范版本、项目适配格式版本。选定规则包版本与摘要继续由项目规则声明和需求投影固定，不在锁定记录重复维护。这些版本可以不同，不能统一替换成一个 v3.1。

本候选先将完整、已校验发行保留于项目 .governance/releases/ 下，便于离线使用与复现。它是固定依赖，通用修复仍回社区源码维护。原生安装及缓存读取已在隔离 CLI/app-server 验证，桌面 UI 交互仍待核验；安装位置不构成版本证明，不能只依赖某个开发者当前的全局技能副本或 latest。

升级后，执行中和历史需求仍能够定位其原规则、工具及来源摘要。更新项目的默认插件版本，不等于已经批准迁移旧需求；不得删除仍被它们依赖的旧版资源后声称兼容。

## 反馈、修复与升级

1. 在项目端定位实际问题，区分通用缺陷、适配缺项和业务代码问题，保存本项目的原始事实及适用版本。
2. 通用缺陷以最小脱敏复现进入社区；社区修复、回归并生成新候选。项目专属约束与业务数据保留在项目仓。
3. 项目端针对指定发行生成升级预览，检查兼容范围、托管文件变化、项目定制、当前未提交修改和在途需求依赖。
4. 没有冲突的获授权改动才应用；冲突明确列出并保留本地内容，不静默覆盖 AGENTS、角色配置或项目脚本。
5. 项目完成适配及必要验证后，更新自己的锁定记录和项目提交。插件上游提交与项目适配提交通过来源版本关联，不要求相同 SHA 或同一次提交。

社区端的通用修复及制品发行、公司端的依赖升级与适配变更分别评审、分别提交到对应仓库。项目端发现的临时修复若具有通用性，先整理回社区，再通过正式发行升级收回项目；不让某个公司的私有修改成为其他项目的隐含依赖。

这描述的是交付模型，不代表本会话已经授权 commit、push、发布或更新公司仓。实际仓库操作仍按各次明确授权执行。

## 当前实现与验证边界

B1、B2、B3 和 C1–C3 提供可复用内核；C4/C5 新增构建清单、技能入口、接入/升级预览、三方冲突保护、固定发行保留与需求绑定。项目脚本的小入口统一转发到运行器，不分别维护治理内核副本；现有副本式项目仍可继续使用原入口。

校验器已区分发行资源根与项目根：在保留发行中执行时，通用规范、Schema 和规则包读取选定发行；领域规范、业务事实及历史 Git 引用仍属于项目。保留默认规范镜像以兼容既有路径；旧需求的实际只读资源不会因镜像升级而切换。

本候选实现以下前四项；双仓闭环仍待公司项目真实试用：

| 工作 | 可审阅成果与验收 |
|---|---|
| 固定版本发行包 | 从确定源码构建清单、技能入口与必要资源，检查漏件及敏感信息；制品可离线校验 |
| 项目初始化与绑定 | 生成适配及锁定预览，保留原 AGENTS 和配置；重复接入无额外差异 |
| 资源定位与运行接入 | 已安装包在不同项目根正常调用工具，现有副本式接入保持兼容 |
| 升级与冲突保护 | 旧发行、新发行和项目定制三方比较；保护未提交修改和仍被引用的旧版依赖 |
| 双仓闭环试用 | 在公司产品开发中使用固定候选，问题脱敏反馈社区，通用修复发行后再升级项目端 |

封装与适配过程中保持范围聚焦：复用现有工具和事实目录，避免再建设一套必须同步维护的项目状态库。B4 前驱契约变更和完整自动续接继续独立跟踪，不因插件化而被视为已经实现。

初版不处理跨治理/测试版本迁移或已有未绑定需求的接管。原生插件安装与技能发现已在隔离 CLI/app-server 实例核验，具体见[原生加载验证](原生加载验证.md)。其他 AI 工具适配继续后置；当前只为 Codex 提供技能和角色入口。隔离合成项目的成功不能代替公司产品开发闭环。
