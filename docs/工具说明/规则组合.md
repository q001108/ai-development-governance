# 规则组合与项目声明（C1–C3 开发候选）

本工具把现有治理核心、可选领域规则、项目参数和本需求适用范围分开处理。它复用既有 RuleId 与开发上下文包的 ApplicableRules 五列表格，不新增验收类别、治理阶段、正式事件或第二套规则编号体系。

当前实现为只读预览与来源核验。RuleCompositionVersion=v1.0、RulePackFormatVersion=v1.0 是工具数据格式，不能据此宣称治理 v3.1 已生效。接入、升级文件写入与冲突合并属于 C4/C5，本候选不执行这些动作，也不覆盖项目 AGENTS、业务源码、历史需求或冻结上下文包。

## 四层来源

| 层次 | 负责内容 | 当前处理 |
|---|---|---|
| 治理核心 | 既有项目开发总则及其 GEN RuleId | 固定到 docs/开发规范/项目开发总则.md 的原始字节 SHA-256；规则包不能覆盖或重定义 |
| 可选规则包 | 前端、后端/API、UI 及明确选择的技术能力规则 | 固定包 ID、版本、清单来源及摘要，再固定规则 Markdown 摘要 |
| 项目声明 | 模块目录、实际能力、规则所需的项目来源 | 接入时从现有项目来源整理一次；不复制实例端口、品牌值或凭据 |
| 本需求投影 | 本次影响模块和直接相关 RuleId | 按能力选择章节默认规则，仅将显式直接相关规则列进原 ApplicableRules 编号列 |

核心规则正文继续以原文为准。规则包正文存于其 rules.md，清单只保存编号、章节、适用能力、参数名和冲突关系；本需求投影不复制正文。没有列为“直接相关”的章节规则仍是默认约束，不把它们逐条变成新的测试或 BA。

## 项目声明

三份可执行的合成样例分别位于：

- [纯后端](../../examples/rules/backend-only/project.json)：仅选择后端/API 包，不出现前端或 UI 义务；
- [Vue 前后端](../../examples/rules/fullstack-vue/project.json)：后端、通用前端及 UI 包；
- [React 前后端](../../examples/rules/fullstack-react/project.json)：复用同一组通用规则，并按显式 react 能力选择额外 FE-101。

这些目录中的契约与模块约定只是假设来源，用于测试格式和组合，不是可部署项目。工具不运行框架、不检查已安装技术版本，也不把能力声明当作实际采用或验证通过。

项目 JSON 固定以下字段：

| 字段 | 作用 |
|---|---|
| RuleCompositionVersion | 固定 v1.0，与治理版本分别表达 |
| GovernanceVersion | 当前已支持的 v3.0 / v3.0.1 / v3.0.2，必须被每个包声明兼容 |
| Core | Source 与原始字节 Sha256；Source 固定到已有项目开发总则 |
| Modules | ModuleId、仓内 Root、Capabilities、Parameters；目录必须存在且互不重叠 |
| Packs | PackId、精确 Version、仓内 JSON Source、原始字节 Sha256；不使用 latest 或远程下载 |

模块 Parameters 的值只在相应规则实际适用时要求存在。FILE_REF 参数引用当前项目已有文件，可附 Markdown 章节锚点，例如样例中的 ApiContract 或 DesignSource。工具记录其读取时的原字节摘要和项目声明位置；该摘要表示本次解析来源，不是项目已经完成审核的证明。CHOICE 参数必须来自包明示的取值集合。参数定义、模板占位符和实际引用必须一致；不同包使用同名参数时，定义必须完全相同，不能静默按包顺序选择一种解释。

规则清单中的 RequiresAll 使用模块 Capabilities 的子集判断；所有条件都满足才适用。配置未声明 data 能力时不会要求 DataContract，也不会默认假设数据库存在。不同项目通过参数文件和能力选择表达差异，不把某个业务项目的目录、框架或视觉品牌写成通用事实。

## 调用与输出

采用候选的项目可将唯一项目声明放在仓库根 governance.rules.json。根 AGENTS 的候选入口要求主智能体在 G1 后已有技术规划中，按实际影响模块自动调用组合工具，将结果引用纳入 DRAFT ApplicableRules；开发者不必逐次输入下面的排查命令。调用方可保存派生 rules-projection.json，B2 会绑定其原始字节，B3 可核对其源摘要。该文件仍是派生投影，不取代正式上下文包，不自行产生批准或要求历史需求迁移。

查看项目整体预览：

```powershell
python scripts/governance_rules.py --repo . --project examples/rules/backend-only/project.json
```

按本次影响模块生成既有 ApplicableRules 表格片段：

```powershell
python scripts/governance_rules.py --repo . --project examples/rules/fullstack-react/project.json --module web --direct-rule FE-001 --format markdown
```

--module 和 --direct-rule 均可重复。模块与直接规则编号应取自已确认的影响分析；调用方不能把目录猜测或全项目选择当成已批准的需求范围。省略模块时 Scope=PROJECT_PREVIEW，显式提供模块时 Scope=AFFECTED_MODULES。两者都固定 RequirementBound=false，不会自动写入任何需求产物。

Python 接口：

```python
compose_rules(repo, project_config, affected_modules=None, direct_rule_ids=None)
verify_composition_sources(repo, projection)
```

结果 ResolvedRules 保留 RuleId、包 ID/版本、Markdown Source/SHA-256、章节锚点、实际适用模块、参数来源和适用原因。Applicability 同时列出 NOT_APPLICABLE 项。ApplicableRules 及 ApplicableRulesMarkdown 使用原有“规范文档、适用章节、直接相关 RuleId、关联控制项、本需求适用说明”五列；关联控制项暂为 N/A，由当前 DRAFT 上下文包按既有工作包与控制引用补齐，工具不自行生成控制 ID。

Sources 保存本次使用的项目声明、包清单、规则文档、参数文件及已读取的项目正式规范的原始字节摘要。verify_composition_sources 仅核对保存的 Sources 集合所列文件字节，不重新选择最新版本；旧来源改变、缺失或路径失效即拒绝。它不验证投影正文是否被改写、Sources 是否被删项或调用者是否获准，因此 Valid=true 只表示所列源文件摘要吻合。投影正文需要重新 compose 后比较，或由现有冻结/事实绑定机制保护。Sources 不是防篡改签名；工具不把本次解析结果冒充已批准、已派发或已通过质量门禁。

投影片段供现有 DRAFT 规划流程引用，不能在同名版本下覆盖 FROZEN 产物。新规则包只影响后续显式选择它的项目和需求，历史需求不自动跟随升级。SOURCE/SHA256 变动应形成新的包版本及项目绑定，不修改原包后沿用固定摘要。

## 与现有工具的兼容边界

当前旧版 governance_tools.py 对 RULE:FE-xxx 等简写只扫描 docs/开发规范 下的正式规则。本工具没有修改它，因此 rulepacks 下的候选规则不能凭编号直接宣称被旧简写校验器支持。

当前投影使用已有“仓内文件#章节锚点”定位规则来源，再在 ApplicableRules 的直接相关编号列列出 RuleId。AcceptancePlan 如需技术来源引用，可使用同一文件#章节方式，并继续由原校验器判断；不能把包来源自动变成 BusinessAcceptanceSources 或 BA。后续文件接入/升级工具将规则放到项目正式位置时，再按显式版本边界处理 RULE: 简写集成。

旧 reference_path 对 docs/scripts/.codex 以外的路径按当前计划目录解析。因此输出另外提供 PlanSourceRefs：以固定 docs/requirements/<RequirementId>/ 为引用基准，为根 rulepacks 生成 ../../../rulepacks/...#章节引用，docs 下的核心来源仍使用仓根路径。ApplicableRules 的来源列仍是人类可读的仓根相对位置，不能把这两种路径基准混用。PlanSourceRefs 已用原 live 计划校验器集成验证，不改变旧解析规则。

## 拒绝与安全边界

- 相同 RuleId 在核心与包之间、多个包之间或包内重复时拒绝，不按顺序覆盖；GEN、TST、ROUTE 以及 BA/RB/QG/AD 控制命名空间保留，包不能重定义；同一包绑定多个版本也拒绝。
- 工具只读检查 docs/开发规范 下已有 Markdown 正式 RuleId 表（上限 128 份），同号来自不同正式来源时拒绝；候选包与项目现有规则同号但源文档不同也拒绝，要求显式适配。已有其他项目规则不会因这次冲突扫描自动加入需求投影。
- 同时适用的规则具有显式 ConflictsWith 时拒绝；冲突引用不存在也拒绝。首轮不推断任意自然语言规则是否语义矛盾，此类冲突仍需审阅。
- 未适用的规则不强制补其参数；已经适用但缺参数、参数不在约定取值内、文件或锚点不存在时拒绝。
- 目录越界、绝对/UNC 路径、反斜杠、符号链接/junction、含 URI 歧义的源路径及常见敏感文件名拒绝。所有来源都必须位于当前仓库，且采集前后的源字节必须一致。
- 单份来源上限 512 KiB，项目最多 64 个模块、32 个包，每包最多 128 条规则；工具不联网、不执行脚本或配置命令，不写文件或治理事实。
- 输入及错误输出进行敏感内容检查；错误仅给通用提示，避免回显路径中的秘密、配置正文或解析异常。

退出码 0 表示来源和组合检查成功；2 表示配置、来源、摘要、冲突或适用条件无法可靠解析。成功退出不表示 G1/G2、需求范围、测试或业务验收通过。

## 验证范围

专用测试使用临时目录中的合成样例，检查后端无 UI、不同前端能力选择、直接规则投影、来源固定、CRLF 字节变化、失效参数、兼容版本、重复与冲突、核心覆盖、路径/符号边界、来源读取中变动、CLI 只读及不执行进程/网络。当前未对公司业务项目进行真实接入或升级，没有外推跨平台或第三方技术栈运行结果。
