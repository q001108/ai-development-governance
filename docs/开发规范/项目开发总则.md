# 通用项目开发总则

> 适用对象：本地开发人员、参与需求实现的 Agent，以及代码评审和验证人员。
>
> 适用范围：接入本治理体系的代码仓库，包括业务源码、测试、配置、脚本和开发文档。
>
> 本文只定义跨项目共同规则；各项目可在 `docs/开发规范/` 下补充自己的领域规范。

## 1. 如何使用这组规范

按任务影响域读取，不要求每次通读全部文档：

| 任务影响 | 必读文档 |
|---|---|
| 初次理解项目、跨模块修改、公共配置或构建调整 | 本总则；必要时读取 `README.md` 和受影响领域规范 |
| 单模块实现 | 本总则 + 当前模块的项目级规范 |
| 页面、组件、主题、响应式或视觉交互 | 本总则 + 项目的前端与设计规范 |
| 服务端、插件、数据库或外部集成 | 本总则 + 项目的后端、数据或集成规范 |
| 跨模块契约、权限或共享数据格式 | 本总则 + 所有受影响领域规范 |

本组文档不保存线上实例状态、部署历史、端口映射、告警阈值、备份步骤或事故记录。会影响代码设计的兼容性、安全、迁移、健康能力和可观测性接口仍属于开发规则；具体运行参数和操作步骤归部署或运维文档。

## 2. 内容归属

| 内容 | 唯一正式归属 |
|---|---|
| 通用修改原则、事实源、敏感信息、兼容性、验证分级和交接 | 本总则 |
| 语言、框架、模块和平台特有约束 | 对应项目级领域规范 |
| 界面、交互、视觉和可访问性 | 对应项目级设计规范 |
| 服务、数据、迁移、事件与集成 | 对应项目级后端或数据规范 |
| 需求范围、验收标准和本次验证集合 | 当前需求的正式输入或开发上下文包 |
| 当前缺陷、技术债和一次性工程快照 | 对应需求记录或问题单，不写入长期规范 |

同一规则只在一个位置正式定义。其他文档需要使用时引用规则编号，不复制正文；禁止事项和评审清单也不得换一种说法重复整套规则。

## 3. 规则表达与事实源

本文使用：

- **必须／禁止**：不可违反的项目约束；
- **应该**：默认选择，偏离时需要有当前任务事实支持；
- **可以**：允许但不强制。

正式规则使用稳定 `RuleId`：

- 本总则使用 `GEN-xxx`；接入项目为领域规则选择稳定且不冲突的前缀；
- 编号不编码章节位置，章节重排时保持不变；
- 规则被替代或废弃时保留旧编号和替代关系，不把旧编号分配给新含义；
- 章节标题和行号只帮助阅读，跨文档或需求引用优先使用 `RuleId`。

编号是文档内的稳定流水号，不是章节号。例如 `GEN-009` 位于第 5 章并不表示编号错误。新增独立规则使用该文档下一个未占用编号，放入语义对应的章节并更新下方索引；不得为了让编号连续地贴合章节而重排旧编号。

只有 `RuleId` 表格中的条目是可以被开发上下文包精确引用的独立正式规则。章节正文、普通表格和示例用于说明范围、事实、背景和如何落实规则；如果一段正文新增了独立的“必须／禁止”义务，应将其提升为带 `RuleId` 的规则。引用整个章节时，其解释和实施指引随章节生效，但不为每段文字另造 `RuleId`。

当前章节索引：

| 章节 | 主题 | RuleId |
|---|---|---|
| 第 4 章 | 通用开发规则 | `GEN-001`～`GEN-008` |
| 第 5 章 | 风险与验证 | `GEN-009`～`GEN-012` |

`RuleId` 用于精确引用高风险或直接相关规则，不是新的逐条打勾清单。任务输入可以用章节引用表达整类常规约束，只对本次风险、验收和验证有直接影响的规则列出具体编号；QA 只执行已经确定的验证集合，Reviewer 也不负责重新枚举整份规范来扩大范围。未被逐项列出的规则仍是领域默认约束，但不得据此在验证阶段临时增加与本次影响无关的检查。

判断项目事实时使用以下顺序：

1. 当前任务已经确认的范围、契约和验收要求；
2. 当前分支的源码、测试、构建脚本和可执行配置；
3. 本总则及适用领域规范；
4. `README`、说明性文档和历史记录。

“当前代码这样做”不自动表示它符合规范，也可能是待修复缺口。源码、配置、测试和规范出现真实冲突时，必须记录冲突并停止依赖该结论，不得静默选择一方，也不得把目标规则写成“当前已经实现”。第三方版本和命令以当前锁文件、POM、`package.json`、插件配置及官方文档为准，不长期复制易漂移的小版本和数量快照。

## 4. 通用开发规则

| RuleId | 级别 | 规则 |
|---|---|---|
| `GEN-001` | 必须 | 修改前读取相关实现、调用关系、配置和测试，确认真实影响范围；不得按文件名或局部片段猜测完整行为。 |
| `GEN-002` | 必须 | 只修改完成当前目标所必需的内容，保持既有接口和无关行为；不得顺手重构、批量格式化或扩大任务范围。 |
| `GEN-003` | 必须 | 优先复用项目现有架构、组件、工具和错误处理方式；新增依赖、体系或公共抽象必须有当前需求和现有能力不足的证据。 |
| `GEN-004` | 必须 | 公共 API、事件、持久化数据、配置键、插件 SPI 和用户可见行为的破坏性变化必须被显式识别，并提供兼容或迁移方案。 |
| `GEN-005` | 必须 | 不得把 API Key、Token、密码、私钥、Cookie、Session、数据库凭据、完整 prompt 或敏感文件内容写入代码、日志、文档、测试证据和提交记录。 |
| `GEN-006` | 必须 | 不得吞掉异常、返回虚假成功或为了通过测试修改无关逻辑；失败信息应保留必要上下文，同时完成脱敏。 |
| `GEN-007` | 必须 | 不直接编辑或提交可由构建生成的产物；验证后检查工作区，区分预期产物、意外副作用和用户原有修改。 |
| `GEN-008` | 应该 | 注释解释约束、原因和非显然失败模式，不翻译代码表面行为；仅在能降低后续维护成本时新增文档。 |

### 4.1 配置与外部依赖

- 可变环境信息通过现有配置体系表达，不在业务代码中硬编码本机路径、端口、主机名或凭据。
- 安全开关默认 fail-closed；无法确认权限、工作区或目标资源时不得放行。
- 外部调用必须有明确超时、取消和资源释放策略；重试应有上限并只覆盖可重试错误。
- 涉及第三方库、SDK、CLI 或配置行为时，先确认项目实际版本，再查询相匹配的官方资料。

## 5. 风险与验证

v3.0.1 新增[测试规范](./测试规范.md)，由明确绑定本社区基线的新需求按影响引用 `TST-001`～`TST-014`。它补充测试基线归因和环境恢复，不替代本节 V0～V3，也不自动展开全量验证；历史需求继续按原绑定规则。

验证档位由影响决定，不按修改文件数、角色数量或文档篇幅机械升级。

| 档位 | 典型影响 | 最低验证 |
|---|---|---|
| `V0` | 纯文档、注释、无行为的元数据 | 检查引用、事实来源、格式和最终 diff；不为此运行无关全量构建 |
| `V1` | 单模块局部行为，公共契约不变 | 静态检查 + 直接相关测试；按风险补充模块构建 |
| `V2` | 跨文件状态、共享组件、API/事件、权限、流式生命周期 | 静态检查 + 定向测试 + 受影响模块测试／构建 + 必要场景验证 |
| `V3` | 数据库迁移、公共 SPI、安全边界、跨模块契约或发布关键路径 | V2 + 兼容性／迁移／集成验证；需要外部环境的项目明确记录条件和结果 |

| RuleId | 级别 | 规则 |
|---|---|---|
| `GEN-009` | 必须 | 修改必须有与风险匹配的验证；未执行、失败、跳过和环境阻塞必须如实记录，不得推断通过。 |
| `GEN-010` | 必须 | 验证命令以当前脚本和配置为准。带 `--fix`、生成源码、迁移数据或改变候选内容的命令不得作为只读检查命令。 |
| `GEN-011` | 必须 | 先执行最小定向验证；只有影响范围或门禁需要时才扩大到模块或全量验证，不因“更严格”无条件重复全部检查。 |
| `GEN-012` | 必须 | 测试验证可观察行为和风险，不为实现细节制造脆弱断言；修复缺陷时优先增加能证明根因和防止回归的测试。 |

领域规范负责给出本领域的命令和高风险场景。若某项验证需要数据库、浏览器、外部服务、凭据或特定操作系统，应在任务开始前确认环境；环境不满足时记录为未验证或阻塞，不把等待环境误判为实现失败。

## 6. 变更完成与交接

完成前至少检查：

- 实际 diff 仍在任务范围内，没有覆盖用户原有修改；
- 公共契约、权限、工作区、敏感信息、迁移和生成产物风险已处理；
- 已执行的验证与修改风险匹配；
- 文档描述的是规则还是现状，两者没有混写；
- 新发现但不属于当前范围的问题已单独指出，没有顺手混入修改。

交接只需说明：修改内容和原因、实际验证及结果、未验证项、残余风险。没有证据的“已通过”“完全兼容”或“当前系统已支持”不得写入结论。

## 7. 维护方式

- 本组规范面向当前代码库持续维护，不绑定某个尚未部署或已经部署的阶段。
- 技术版本、脚本名称和能力状态尽量引用权威配置；只有会改变开发选择时才在规范中列出。
- 发现实现不符合规则时，将其登记为缺陷或技术债；除非任务明确要求，不通过放宽规则掩盖问题。
- 规则含义变化时同步检查领域规范和开发上下文包模板中的引用方式；不得把 `RuleId` 扩展成角色逐条检查清单。
